# 修复 Chat 范围契约测试中的编码与断言退化

## 基本信息
- 类型：bug
- 日期：2026-07-24
- 相关模块：Chat 范围控制契约、API 测试
- 相关文件：`api/services/query_scope.py`、`tests/api/test_chat_scope_contract.py`

## 问题现象
`query_scope.py` 和 `test_chat_scope_contract.py` 里的中文注释、文档字符串和部分断言字符串在落盘时被写成了字面量问号。测试虽然还能通过，但像 `assert "????" in resp.json()["message"]` 这样的断言已经失去语义约束，无法真正验证错误消息是否符合契约。

## 根因分析
这不是运行时逻辑错误，而是文件写入阶段的文本编码退化问题。源码里的中文提示语被损坏后，测试文件用同样损坏的字符串去匹配后端返回值，导致“坏消息匹配坏断言”也能通过，掩盖了契约验证缺口。

## 解决方案
1. 重写 `api/services/query_scope.py` 中损坏的中文模块说明、类说明、函数说明和错误提示语，恢复可读的 UTF-8 文本。
2. 重写 `tests/api/test_chat_scope_contract.py` 中损坏的中文注释。
3. 将无效的问号断言替换为真正有业务语义的断言，分别校验“显式声明单库”“范围不能为空”“不支持多知识库查询”“知识库不存在”“知识库不可用”等错误消息片段。
4. 重新执行 Chat 范围契约相关测试，确认修复没有影响 P0-1 的 default-deny 行为。

## 为什么选这个方案
这是最小且直接的修复路径：不改变既有契约，只恢复文本与断言的表达能力。相比重构测试结构或调整异常类型，修复编码和断言内容的成本最低，也最能快速补上测试有效性缺口。

## 其他方案与为什么没选
- 方案一：只保留状态码断言，不校验错误消息。没选，因为 P0-1 的范围契约本身就包含明确的拒绝原因，仅验证 4xx 会弱化接口契约。
- 方案二：统一把错误消息改成英文常量。没选，因为仓库规范要求中文注释/文档，且当前 API 面向本地中文产品语境，额外引入文案改造超出本次修复范围。

## 验证与结果
- 执行命令：`python -m pytest tests/api/test_chat_scope_contract.py tests/api/test_m2_multi_kb.py -q`
- 结果：`34 passed`
- 结论：Chat 范围 default-deny 主链路保持稳定，测试现在能真实验证错误消息语义，不再依赖损坏的问号字符串。

## 面试表达版本
我在收紧 Chat 单库范围契约后，发现测试虽然是绿的，但其实有一类“假通过”问题：中文字符串在写文件时退化成了问号，测试也拿问号去断言问号。我没有去改主流程逻辑，而是先把 `query_scope.py` 和对应测试文件里的中文说明、错误消息和断言全部恢复成真实语义，再用现有的 scope contract 测试回归。这样做的价值是把“能跑通”修成了“能真正验证契约”，避免后续有人以为 default-deny 已经被严格覆盖，实际上只是被损坏字符串掩盖了。
