代码与测试报告评审建议（2026-08-14，macOS 单次公证与多凭证策略）

评审结论：
本轮实现与已审核的 PRD、FRD、RTM、实施计划和测试方案一致。共享凭证解析、单次公证配置不变量、严格预检诊断、真实非正式打包及跨层回归均有直接证据，测试报告已更新，可以进入开发故事沉淀和提交阶段。正式 Apple 签名、公证、stapling 与安装后回归仍属于明确记录的外部凭证阻塞，不得在当前提交中标记为完成。

优点：
1. `notarization-credentials.js` 作为纯解析模块同时被 `notarize-mac.js` 和 `release-preflight.js` 复用，避免 hook 与预检对凭证完整性和优先级产生漂移。
2. Keychain profile、App Store Connect API Key、Apple ID 三种策略的 payload 与优先级均有单测；最高优先级部分配置不会阻止后续完整策略，诊断保留缺失字段但不泄露凭证值。
3. `build.mac.notarize=false` 与 `afterSign=scripts/notarize-mac.js` 共同形成单次提交不变量，配置校验器对缺失和 `true` 都失败；真实 `build:mac` 已证明 electron-builder 26.15.3 接受该配置且只进入一次自定义 hook。
4. 严格 preflight 改为汇总独立硬门禁，一次输出公证凭证、Developer ID Application 和 notarytool 状态，避免发布人员逐项修复后反复运行才发现下一处缺失。
5. 测试证据完整：Electron `64 passed`，Python `783 passed, 1 deselected`，Web `89 passed` 且 Vite build 通过；`build:preflight`、真实 `build:mac` 和 `verify:package` 均通过。

需要改进的地方：
1. 当前机器没有有效 Developer ID Application 身份，也没有任一完整公证凭证策略，因此只能验证“配置单次提交”和“无凭证时 hook 单次安全跳过”，不能验证 Apple 服务侧真实 submission、accepted 状态和 stapled ticket。
2. 当前生成的 app 仍是 ad-hoc 产物，非严格 `verify-mac-release` 会报告 codesign、Gatekeeper 和 stapler 失败；这不是本轮代码回归，但正式发布前必须关闭。

具体建议：
1. 保持当前代码和测试实现，不再扩大本提交范围。
2. 提交前生成本轮 bug 开发故事并推进 capture state；执行 `git diff --check` 和最终桌面定向门禁。
3. Apple 凭证到位后严格按 release checklist 执行 `release:preflight`、`release:mac`、`verify:package`、`verify:mac-release` 和安装后桌面工作流，并保留仅一次 notarization submission 的真实日志证据。
