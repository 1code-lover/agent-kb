测试与评测阶段复核意见（2026-07-31，最新）

优点：
1. 这轮对“答案过短”问题没有停留在报告备注层，而是先补了失败测试，再把修复落在 `api/services/chat_service.py` 的 source-backed 最小完整句补全逻辑里，做法符合 TDD 和真实问题驱动的要求。
2. 修复验证链条完整：`tests/api/test_chat_service.py` 新增的两条用例已经覆盖“可扩写/不可扩写”两种边界，受影响问答回归 `86 passed`，没有通过放松断言来制造通过。
3. live 证据闭环这次补齐了。`diag-utf8-after-answer-expand.json` 已确认回答从“知识库”提升为“知识库仍然是授权边界。”，而且 `chat_answer_contains_expected_snippet` 等关键 gate 全部转为 true，这说明修复不仅在单测里成立，也在真实本地服务 roundtrip 里成立。
4. 这次修复没有破坏已有安全/契约语义：拒答裁剪、scope echo、evidence / preview 契约、semireal Markdown/PDF/图片/mixed batch 问答回归都仍然通过，说明改动边界控制得比较克制。
5. 测试报告同步得比较及时，已经把 UTF-8 live 短答案从“当前缺口”更新成“已修复并纳入回归”，避免后续读者继续按旧结论理解现状。

需要改进：
1. `api/services/chat_service.py` 目前为兼容 shell 编码问题，部分中文文档字符串使用了 `\u` 形式写法；功能上没问题，但后续如果继续整理代码可读性，仍建议在确保 UTF-8 安全的前提下恢复为直写中文。
2. live 诊断脚本的启动与端口管理仍略脆弱，手工拉起新服务时容易碰到端口占用或旧进程残留。后续如果继续依赖 live roundtrip 做常规验收，最好补一个统一的启动/探活/清理封装。
3. mixed batch live 诊断与正式 eval 的 `source/evidence count` 口径差异依旧存在；这轮没有阻断，但它已经成为报告里长期重复出现的“诚实说明”，后续最好制度化收敛。
4. 当前对“最小完整句补全”的测试仍集中在 UTF-8/Markdown 场景；如果后面继续优化答案质量，建议把 PDF / OCR 来源下的短答案场景也加入评测集，防止只修一个 fixture。

具体建议：
1. 下一步研发重点可以明确转向两条：
   - 扩展问答质量评测集，覆盖更多“答案过短 / 表达不完整 / 证据够但措辞弱”的真实场景；
   - 继续完善 live 诊断脚本的工程化稳定性（端口、进程、artifact 命名、失败时日志采集）。
2. 若准备继续提交当前阶段代码，先把这次新增的诊断产物与必要临时日志做一次筛选，保留正式 artifact，避免把无关 tmp 文件一并带入提交面。
3. 在后续质量文档里，可以把“source-backed 最小完整句补全”正式登记为一条问答后处理策略，并注明触发条件：仅限非拒答、实体型问题、短答案、且 source/excerpt 能直接支撑更完整子句时触发。
4. 后续如果要做更系统的问答质量优化，不要直接扩大启发式规则，而应优先通过评测数据集先定义缺口，再决定是继续做后处理、检索优化，还是改 prompt / answer synthesis。
