## 2. 背景与目标

### 2.1 背景

当前系统的 Agent 智能体已具备基本能力（kb_search、read_file、run_cmd、llm_chat 四个工具），但存在以下问题：

1. **知识库搜索硬编码**：`run_kb_search()` 默认只搜索 default 知识库，无法利用已创建的多个知识库
2. **单知识库限制**：`KnowledgeScope` 只支持单个 `kb_id`，无法同时检索多个知识库
3. **chat_service 不支持指定知识库**：`chat_service.query()` 没有 `kb_id` 参数，无法将检索限定到特定知识库
4. **缺乏智能选择**：用户无法让 Agent 根据问题自动判断该搜哪个知识库

### 2.2 目标

- 支持多知识库并行检索
- LLM 自动选择最相关的知识库进行搜索
- 检索结果标注来源知识库，支持溯源
- 用户可以指定候选知识库范围（可选全部）

### 2.3 非目标

- 不实现知识库间的知识图谱关联
- 不实现跨知识库的语义去重（后续优化）
- 不修改现有知识库管理的 CRUD 接口

## 3. 用户场景

### 场景 1：用户提问，Agent 自动选择知识库

```
用户："我们公司的报销流程是什么？"
Agent 内部：
  1. LLM 识别到"报销流程"属于"公司制度"知识库
  2. 调用 kb_search(kb_ids=["kb_公司制度"], query="报销流程")
  3. 检索结果标注来源：[公司制度] 报销需在3个工作日内提交...
Agent："根据公司制度知识库，报销流程如下：..."
```

### 场景 2：问题涉及多个知识库

```
用户："Python 项目如何部署到公司的 Kubernetes 集群？"
Agent 内部：
  1. LLM 识别到问题同时涉及"Python 技术文档"和"运维部署手册"
  2. 并行调用：
     - kb_search(kb_ids=["kb_python"], query="Python 部署")
     - kb_search(kb_ids=["kb_运维"], query="Kubernetes 部署")
  3. 合并结果，去重排序
Agent："结合 Python 文档和运维手册，部署步骤如下：..."
```

### 场景 3：用户指定候选知识库范围

```
用户："只在技术文档里搜索 FastAPI 的用法"
Agent 内部：
  1. 用户明确指定了"技术文档"知识库
  2. 调用 kb_search(kb_ids=["kb_技术文档"], query="FastAPI 用法")
Agent："根据技术文档，FastAPI 的用法如下：..."
```

## 4. 功能需求

### 4.1 多知识库搜索工具增强

**需求 ID：** F-KB-001

**描述：** `run_kb_search` 工具支持传入多个知识库 ID，并行检索并合并结果

**验收标准：**
- [ ] `kb_ids` 参数接受 `List[str]`，支持传入多个知识库 ID
- [ ] 同时检索多个知识库，结果按相关性合并排序
- [ ] 每条检索结果标注来源知识库名称
- [ ] 向后兼容：不传 `kb_ids` 时仍搜索默认知识库

### 4.2 LLM 自动选择知识库

**需求 ID：** F-KB-002

**描述：** Agent 的 LLM 根据用户问题自动判断应该搜索哪些知识库

**验收标准：**
- [ ] LLM system prompt 中注入所有可用知识库的描述信息
- [ ] LLM 能根据问题内容选择 1 个或多个最相关的知识库
- [ ] 选择结果作为 `kb_search` 工具的 `kb_ids` 参数传入
- [ ] 提供 fallback 机制：当 LLM 无法判断时搜索所有知识库

### 4.3 chat_service 支持指定知识库

**需求 ID：** F-KB-003

**描述：** `chat_service.query()` 接受可选的 `kb_id` 参数，将检索限定到特定知识库

**验收标准：**
- [ ] `query()` 方法增加 `kb_ids: Optional[List[str]]` 参数
- [ ] 传入 `kb_ids` 时，QueryEngine 只在指定知识库中检索
- [ ] 不传时保持原有行为（搜索默认知识库）

### 4.4 KnowledgeScope 支持多知识库

**需求 ID：** F-KB-004

**描述：** `KnowledgeScope` schema 改为支持多个知识库 ID

**验收标准：**
- [ ] `kb_id` 字段改为 `kb_ids: List[str]`
- [ ] `kb_name` 字段改为 `kb_names: List[str]`
- [ ] 向后兼容：单个 ID 也能正常工作

### 4.5 检索结果溯源标注

**需求 ID：** F-KB-005

**描述：** 每条检索结果标注来源知识库，方便用户溯源

**验收标准：**
- [ ] 检索结果包含 `kb_name` 字段
- [ ] LLM 回答时引用知识库来源
- [ ] 前端展示时标注结果来自哪个知识库

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 多知识库并行检索，总延迟不超过最慢单库检索的 1.5 倍 |
| 可用性 | 向后兼容，现有单知识库使用不受影响 |
| 可扩展性 | 支持未来扩展到 10+ 知识库 |

## 6. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| LLM 选错知识库 | 检索结果不相关 | 给知识库加详细描述；提供 fallback 搜全部 |
| 多库结果冲突 | 回答矛盾 | LLM 综合时标注来源差异 |
| 检索延迟增加 | 用户体验下降 | 并行检索；设置超时 |

## 7. 成功指标

| 指标 | 目标 |
|---|---|
| 多知识库检索准确率 | >= 80%（LLM 选对知识库的比例） |
| 端到端回答质量 | 用户满意度 >= 85% |
| 检索延迟 | P95 < 5 秒 |
