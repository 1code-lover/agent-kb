# 多知识库目录化存储 PRD

- 日期：2026-07-14
- 专题：一个目录对应一个知识库
- 状态：待评审
- 关联现状：`docs/spec/knowledge_base_visibility_and_multi_kb_design.md`

## 1. 背景

当前项目已经具备知识库 registry、KB CRUD、导入时写入 `kb_id` metadata、查询时接收 `kb_ids` 等最小多知识库能力，但原始上传文件仍平铺保存在 `data/` 根目录，向量数据仍持久化在共享的 `storage/` 中。

当前真实形态是：

- `storage/kb_registry.json` 记录知识库目录；
- `data/` 下不同知识库文件混放；
- `storage/` 下使用一个共享索引；
- 查询依赖节点 `kb_id` metadata 做范围过滤。

用户确认下一步采用：**在 `data/` 下建立多个文件夹，一个文件夹对应一个知识库。**

## 2. 目标

1. 每个已登记知识库都有唯一原始文件目录：`data/{kb_id}/`。
2. 文件导入时必须先确认 `kb_id` 已登记，并只写入该知识库目录。
3. 文档列表、删除和后续迁移能够根据 `kb_id` 找到明确的物理文件归属。
4. 保持现有 API 的 `kb_id` / `kb_ids` 契约兼容。
5. 为后续用户提供的真实问答建立可版本化的多知识库质量评测数据格式。
6. 文档中明确区分“原始文件目录隔离”和“向量索引物理隔离”。

## 3. 非目标

本专题第一阶段不包含：

1. 每个知识库独立向量数据库、独立 LlamaIndex `StorageContext` 或独立 namespace。
2. 用户、角色、组织和权限可见性控制。
3. 自动把未经人工确认的问题和答案直接当成正式 ground truth。
4. 在未完成备份、迁移验证前自动移动或删除现有 `data/`、`storage/` 数据。
5. 用文件夹扫描结果替代 `storage/kb_registry.json`；registry 仍是知识库身份的权威来源。

## 4. 目标目录结构

```text
data/
  default/
    existing-document.pdf
  product-docs/
    product-guide.pdf
    release-notes.txt
  ops-manual/
    deploy-guide.md

storage/
  kb_registry.json
  docstore.json
  index_store.json
  default__vector_store.json
```

说明：

- `data/{kb_id}/` 保存知识库原始文件。
- `storage/kb_registry.json` 保存知识库身份、名称、状态和统计信息。
- 第一阶段仍保留共享索引，所以 `storage/` 暂不按知识库拆目录。
- 文件目录存在不代表该知识库已经完成索引；索引成功状态必须以导入结果和 registry 状态为准。

## 5. 用户场景

### US-01 创建知识库

用户创建 `product-docs` 后，系统登记 registry，并创建 `data/product-docs/`。

### US-02 导入文件

用户向 `product-docs` 上传文件，文件只能落到 `data/product-docs/`，索引节点必须携带 `kb_id=product-docs`。

### US-03 查看和删除文档

用户选择某个知识库后，只能看到该库文档。删除索引文档时，系统应同步处理对应源文件，且不能越过知识库目录边界。

### US-04 删除知识库

第一阶段不允许静默级联删除非空知识库。知识库有文档时返回冲突错误；为空时才允许删除 registry 项和对应空目录。

### US-05 多知识库问答评测

用户提供更多真实问答后，系统维护每个问题的目标知识库、标准答案和证据片段，分别检测检索质量和答案质量。

## 6. 功能需求

### FR-01 知识库目录生命周期

- 创建知识库成功后必须存在 `data/{kb_id}/`。
- 默认知识库启动初始化时必须确保 `data/default/` 存在。
- 更新知识库名称不重命名目录，因为 `kb_id` 不可变。
- 删除空知识库时删除空目录；非空知识库删除返回 409。

### FR-02 路径安全

- `kb_id` 只允许小写字母、数字和中划线，长度 1-64，首尾必须是字母或数字。
- 服务端根据 `kb_id` 计算目录，不接受客户端传入任意磁盘路径。
- 文件最终路径必须通过绝对路径边界校验，保证位于 `data/{kb_id}/` 内。
- Windows 保留名称和路径穿越形式必须拒绝。

### FR-03 文件导入

- 导入前校验 `kb_id` 是否存在且状态为 `active`。
- 保存路径调整为 `data/{kb_id}/{unique_filename}`。
- 索引节点 metadata 至少包含 `kb_id`、`file_name`、`file_path`。
- 文件保存成功但索引失败时，必须返回明确失败结果，不得增加成功文档计数。

### FR-04 文档管理

- 按 `kb_id` 列表查询时，不得把其他库文档或无 `kb_id` 的旧节点混入非 `default` 库。
- 删除文档必须同时限定 `kb_id` 和文档标识。
- 删除源文件前必须再次验证文件路径位于目标知识库目录内。

### FR-05 registry 一致性

- registry 是知识库权威清单，目录扫描不得自动创建未登记知识库。
- registry 创建和目录创建需要失败回滚，避免只成功一半。
- `doc_count` 只能在索引成功后增加，在索引和文件删除成功后减少。

### FR-06 存量数据迁移

- 现有 `data/` 根目录文件默认归属 `default`。
- 首选策略是备份后重新导入并重建索引，使 `file_path` 和 `kb_id` metadata 同步更新。
- 迁移必须有 dry-run、备份、执行结果和回滚说明。
- 本需求评审通过前不移动现有文件。

### FR-07 问答评测数据接收

用户可以先提供自然语言形式的“问题 + 参考答案”。整理后形成以下字段：

```json
{
  "id": "qa-001",
  "query": "如何创建产品知识库？",
  "search_kb_ids": ["product-docs"],
  "expected_answer": "……",
  "relevant_documents": [
    {
      "kb_id": "product-docs",
      "file_name": "product-guide.pdf",
      "evidence": "……"
    }
  ],
  "answerable": true,
  "difficulty": "medium",
  "tags": ["kb-management"]
}
```

规则：

- 用户只给问题和答案时，可以先进入 `draft`，但在找到证据文件和证据片段前不能进入正式回归集。
- 支持单库、多库和无答案三种用例。
- 正式集与临时合成集分开版本化，避免把探索样本当成生产质量结论。
- 草稿和正式集固定保存到 `tests/fixtures/rag_quality/draft.jsonl`、`tests/fixtures/rag_quality/verified.jsonl`，不得放入 `data/{kb_id}/` 或其他会被索引的目录。
- 正式回归集目标不少于 50 条，并按简单、中等、复杂分层统计。

## 7. 非功能需求

1. Windows 路径处理必须使用 `pathlib.Path` 或等价安全方式。
2. 目录创建、查询和删除应有单元测试和 API 集成测试。
3. 现有单库调用不传 `kb_id` 时仍默认使用 `default`。
4. 迁移前后必须可核对文档数、节点数、文件哈希和检索命中。
5. 运行日志不得记录 API Key 或文档敏感正文。

## 8. 验收标准

1. 创建两个知识库后，存在两个独立目录，registry 中也有两条对应记录。
2. 分别向两个知识库上传同名文件，不发生覆盖，文件位于各自目录。
3. 导入未知或非法 `kb_id` 返回 400，磁盘不产生目录或文件。
4. 查询某个知识库的文档列表，不出现其他知识库文档。
5. 删除非空知识库返回 409；删除空知识库后 registry 和空目录同时消失。
6. 现有 `default` 调用保持兼容。
7. 至少完成一组双知识库隔离测试和一组多知识库联合查询测试。
8. 用户提供的问答可以转换为结构化草稿集，并能检查 ID、目标库和证据字段完整性。

## 9. 当前结论

当前“可以使用”和本专题“可以开始构建”必须区分：

| 能力 | 当前可以使用 | 本专题待实现 |
|---|---|---|
| KB registry 与 CRUD | 已可用于开发联调 | 补齐目录创建/删除的一致性回滚 |
| 单库/多库查询范围 | 已接收 `kb_ids`，在共享索引检索后按 metadata 过滤 | 不在本阶段改成独立索引，但要用真实评测记录后置过滤风险 |
| 原始文件存储 | 文件仍平铺在 `data/` 根目录 | 改为 `data/{kb_id}/`，建立严格文件归属 |
| 文档列表与删除 | 已有接口，但旧无标签数据兼容较宽松 | 按 `kb_id` 收紧列表、删除和源文件路径边界 |
| 存量数据 | 尚未完成目录化迁移 | 备份、dry-run、重导并重建索引，默认归入 `default` |
| 正式 QA 评测集 | 目前只有小规模合成烟测，不是正式业务集 | 在仓库固定路径维护 draft/verified，用证据绑定后做回归 |

因此，**当前逻辑多知识库可以做开发联调，但 `data/{kb_id}/` 目录化存储、严格文件归属和存量迁移尚未实现，也没有完成新需求测试。**

该需求可以开始构建，而且与当前 registry + `kb_id` metadata 方案兼容。第一阶段的正确定位是：

> **多知识库逻辑隔离 + 原始文件物理分目录 + 共享向量索引。**

若后续要求不同知识库在向量存储层完全隔离，应另行评审 `storage/kbs/{kb_id}/` 多索引方案，不能仅凭 `data/{kb_id}/` 宣称已经实现物理索引隔离。
