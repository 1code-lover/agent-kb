## 2. 文档目的

本 Spec 不是重复 PRD / FRD，而是把“这个项目到底是什么、内部知识对象如何组织、导入与嵌入链路怎么设计、将来怎么扩展到 Agent 与更多模态”讲清楚。

这份文档重点回答 7 个问题：
1. 这个项目的产品定位到底是什么，不是什么；
2. 知识库、文件夹、文档、资产、Chunk 之间是什么关系；
3. 知识库内部是否应该有文件夹，以及文件夹处在什么层级；
4. Markdown、PDF、图片、流程图这类内容应该怎样进入统一知识体系；
5. 导入、重导入、删除、重建索引分别是什么动作，边界如何区分；
6. 当前共享单索引的现实与未来“知识库是一等对象”的目标之间，差距在哪里；
7. 后续如果接入外部 Agent 或其他 Agent 项目，应该留什么契约。

## 3. 产品定位

### 3.1 一句话定位

这是一个**面向个人 / 小团队的、本地优先、多知识库、可证据化、可扩展到 Agent 接入的知识助手平台**。

### 3.2 它首先是什么

它首先是一个“知识底座平台”，而不是一个单纯的聊天壳子。

它的核心价值不是“能不能问答”，而是：
1. 能不能把知识**长期稳定地导入、组织、更新、删除、重建**；
2. 能不能把不同知识库当成**一级对象**来管理；
3. 能不能把回答建立在**明确范围、明确证据、明确来源定位**之上；
4. 能不能为未来接入更多模态与 Agent 保留稳定契约。

### 3.3 它不是什么

当前阶段它不是：
1. 企业级多租户权限系统；
2. 在线 SaaS 知识管理平台；
3. 通用文件网盘；
4. 以“多用户协同编辑”为核心的内容生产系统；
5. 纯粹追求大而全模型能力的聊天产品。

### 3.4 目标用户

当前优先服务的用户：
1. 有大量本地文档的个人知识工作者；
2. 有项目资料、规范、流程、会议材料的研发 / 产品 / 运营团队；
3. 想把自己的文档库作为本地 AI 助手底座的人；
4. 未来想把知识库开放给 Agent 使用，但又不希望 Agent 默认看到全部内容的人。

### 3.5 核心价值主张

这个平台要解决的不是“有没有聊天框”，而是以下 4 个问题：
1. **多知识库管理**：不同主题、不同项目、不同边界的知识不能混成一个大仓；
2. **多模态知识接入**：不仅是 Markdown 和 PDF 文本，还包括图片、扫描件、流程图等；
3. **证据化回答**：回答必须能指回文档、页码、片段、预览位置；
4. **面向扩展的底座**：以后要接 Agent、接其他工具、接外部工作流时，不用推翻底层对象模型。

## 4. 当前现实与目标态

### 4.1 当前现实

当前代码基础已经具备：
1. 本地文件导入、URL 导入、索引、检索、问答的主路径；
2. Markdown / PDF 文本处理能力；
3. PDF 文字层抽取与 OCR 回退；
4. Chat 范围 default-deny；
5. 证据对象与文档预览主链路雏形；
6. 多知识库“逻辑能力”的最初实现。

### 4.2 必须诚实承认的架构现实

当前的多知识库并不是存储隔离意义上的一等对象，而是：
1. 所有知识库共享单一 docstore / vector store / index store；
2. 依赖 `metadata["kb_id"]` 来做检索时过滤；
3. 边界本质上仍是**逻辑过滤**，不是**物理隔离**；
4. 因此任何过滤逻辑失效，都有跨库泄露风险。

### 4.3 目标态

目标态不是“继续把 `kb_id` tag 补补缝缝”，而是：
1. KnowledgeBase 是一级产品对象；
2. 知识范围控制是显式契约，不是隐式默认；
3. Folder / Document / Asset / Chunk / Evidence 都有明确对象语义；
4. 导入与嵌入是可追踪、可回执、可恢复的流程；
5. 将来可以从逻辑隔离平滑演进到物理隔离或命名空间隔离。

### 4.4 关键判断

因此，这个项目当前真正要做的，不是继续堆更多表面功能，而是先把“知识底座”立住：
- 边界模型立住；
- 对象模型立住；
- 导入回执立住；
- 证据契约立住；
- 扩展接口立住。

## 5. 设计原则

### 5.1 KnowledgeBase 是边界对象
知识库负责：
- 查询范围；
- 归属范围；
- 授权范围；
- 生命周期范围；
- 后续物理隔离的演进锚点。

### 5.2 Folder 是组织对象，不是边界对象
文件夹可以有，而且应该有；但它的定位是：
- 目录组织；
- 导入映射；
- 浏览导航；
- 检索收窄辅助。

文件夹不是：
- 主权限边界；
- 主隔离边界；
- 主存储边界。

### 5.3 Document / Asset / Chunk 分层，不揉成一个概念
- `Document`：知识来源对象；
- `Asset`：文档内部或独立存在的图像/流程图/附件等知识资产；
- `Chunk`：检索与嵌入的主处理单元。

### 5.4 默认显式边界
任何问答、Agent 调用、检索调用都不应该默认“查全部”。

### 5.5 证据优先
回答结果必须能够追溯到：
- 来自哪个知识库；
- 哪个文档；
- 哪个片段或页；
- 如何预览。

### 5.6 先做稳定 ingestion，再做高级多模态
在导入链路不稳定前，不适合直接上复杂的资产模型与高级嵌入策略。

### 5.7 面向演进而不是一步到位
P0 不要求所有能力全部做满，但要求对象模型和接口方向不能走偏。

### 6.1 顶层结构

   │  └─ Document
   │     ├─ Asset
   │     └─ Chunk
   ├─ Document

   │  └─ Chunk

### 6.2 推荐的产品视图分层

#### 6.2.1 管理层
用户能看到：
- 知识库列表；
- 每个知识库的状态；
- 文件夹树；
- 文档列表；
- 资产列表；
- 导入记录 / 回执。

#### 6.2.2 内容层
系统内部管理：
- 文档正文；

#### 6.2.3 处理层
系统负责：
- 解析；
- 切分；

#### 6.2.5 接口层
对 Chat / Agent / 外部工具暴露：

## 7. 知识库内部是否应该有文件夹

### 7.1 结论

**应该有。**

而且对于你这个项目，文件夹不是“可有可无的小功能”，而是后续可维护性的基础组织结构。

### 7.2 为什么需要文件夹

因为真实知识库不会只有几十个平铺文件。你后续一定会遇到：
- 产品文档；
- 研发设计；
- API 文档；
- 流程规范；
- 周报 / 纪要；
- 项目截图与流程图；
- PDF 附件与扫描页。

没有文件夹时，会出现 4 个问题：
1. 用户浏览成本高；
2. 目录导入时无法保留原有语义结构；
3. 相对路径资源（尤其 Markdown 图片）难以定位；
4. 后续局部收窄检索不方便。

### 7.3 文件夹的正确定位

文件夹的职责是：
1. 保留用户原始目录语义；
2. 提供树状浏览；
3. 作为导入来源路径映射；
4. 提供“可选的局部收窄范围”。

文件夹**不是**：
1. 默认权限边界；
2. 多知识库替代品；
3. 独立物理存储边界；
4. 默认主查询边界。

### 7.4 推荐层级

```text
知识库 KB
├─ 文件夹 Folder
│  ├─ 子文件夹 Folder
│  │  └─ 文档 Document
│  └─ 文档 Document
└─ 文档 Document
```

### 7.5 目录导入默认策略

目录导入时，默认采用：
**保留源目录树结构**。

也就是说：
- 用户从本地导入一个目录；
- 系统在该知识库内创建对应 Folder 树；
- 文档按相对路径挂入对应 Folder；
- Markdown 中相对路径图片也优先按该相对关系解析。

### 7.6 文件夹与检索的关系

P0 阶段建议：
- 主检索边界仍是 `kb_id`；
- Folder 作为展示与后续扩展维度先建模；
- 可以预留 `folder_ids` 过滤，但不强制作为主路径。

## 8. 核心对象模型

### 8.1 KnowledgeBase

#### 8.1.1 定义
一个知识库是一组共享语义边界、共享管理边界、共享查询边界的知识对象集合。

#### 8.1.2 最小字段建议
- `kb_id`
- `kb_name`
- `description`（可选）
- `status`：`active / inactive / rebuilding / error`
- `doc_count`
- `asset_count`
- `created_at`
- `updated_at`
- `storage_mode`：`logical_filter_only / namespace / physical_isolated`

#### 8.1.3 说明
当前实现现实上仍是 `logical_filter_only`，必须在文档与接口回执中诚实体现。

---

### 8.2 Folder

#### 8.2.1 定义
Folder 是知识库内部的组织目录对象，用于表达层级结构与来源路径。

#### 8.2.2 最小字段建议
- `folder_id`
- `kb_id`
- `parent_folder_id`
- `name`
- `path`
- `source_path`（本地目录导入时可选）
- `created_at`
- `updated_at`

#### 8.2.3 关键约束
- Folder 必须从属于某个 `kb_id`；
- Folder 可以嵌套；
- Folder 不能跨知识库移动；
- Folder 不是授权边界对象。

---

### 8.3 Document

#### 8.3.1 定义
Document 是用户可理解、可管理、可删除、可预览的知识来源对象。

#### 8.3.2 类型示例
- Markdown 文档
- PDF 文档
- Word / 文本类文档
- URL 导入网页
- 图片文件（作为独立文档导入时）

#### 8.3.3 最小字段建议
- `doc_id`
- `kb_id`
- `folder_id`（可为空）
- `title`
- `source_type`：`file / url / generated`
- `mime_type`
- `source_uri` 或 `file_path`
- `checksum`
- `status`：`indexed / empty / failed / deleted / pending`
- `ingestion_receipt_id`
- `created_at`
- `updated_at`

#### 8.3.4 设计判断
即使当前底层索引里还没有完整的文档表，也应该先在产品与接口语义上把 `Document` 明确成一等对象。

---

### 8.4 Asset

#### 8.4.1 定义
Asset 是文档内部或独立存在的可引用知识资产。

#### 8.4.2 典型资产类型
- Markdown 内嵌图片
- 流程图截图
- PDF 页内图表
- 扫描页图像
- 独立上传图片

#### 8.4.3 为什么 Asset 要单独建模
如果把图片只当“附件”，会有 4 个问题：
1. 不能独立被检索命中；
2. 不能直接作为证据引用；
3. 不能记录 OCR / caption / page 定位；
4. 后续做视觉理解时缺少稳定对象锚点。

#### 8.4.4 最小字段建议
- `asset_id`
- `kb_id`
- `doc_id`
- `folder_id`（可选）
- `asset_type`：`image / diagram / page_image / attachment`
- `asset_role`：`embedded / standalone / extracted`
- `source_path` 或 `source_locator`
- `page_number`（适用于 PDF）
- `caption_text`（可选）
- `ocr_text`（可选）
- `status`
- `created_at`
- `updated_at`

---

### 8.5 Chunk

#### 8.5.1 定义
Chunk 是当前 P0 阶段最主要的检索与嵌入处理单元。

#### 8.5.2 来源
Chunk 可以来自：
- 文档正文切分；
- OCR 结果切分；
- Asset 文本化结果切分；
- 网页正文抽取。

#### 8.5.3 最小字段建议
- `chunk_id`
- `kb_id`
- `doc_id`
- `asset_id`（可为空）
- `chunk_type`：`text / ocr / caption / mixed`
- `text`
- `token_count`
- `source_locator`
- `embedding_status`

---

### 8.6 EmbeddingRecord

#### 8.6.1 定义
EmbeddingRecord 表示某个 Chunk 的向量化状态与元信息。

#### 8.6.2 最小字段建议
- `embedding_id`
- `chunk_id`
- `kb_id`
- `model`
- `dimension`
- `status`
- `embedded_at`
- `index_namespace`（未来可用）

#### 8.6.3 说明
P0 不一定单独持久化成完整业务表，但设计上应承认这是一类独立状态，而不是“向量写进去就完了”。

---

### 8.7 IngestionJob / Receipt

#### 8.7.1 定义
IngestionJob 表示一次导入与索引过程；Receipt 表示这次过程的回执视图。

#### 8.7.2 当前阶段建议
P0 不必立刻做完整任务系统，但至少要有：
- `receipt_id`
- 每项输入的结果状态
- `success_count`
- `failed_count`
- `empty_count`
- `indexed_chunks`

#### 8.7.3 为什么必须有回执
因为用户和后续系统都需要知道：
- 哪些文件真的入库了；
- 哪些只是落盘但没索引出内容；
- 哪些失败了；
- 失败原因是什么。

---

### 8.8 Evidence

#### 8.8.1 定义
Evidence 是回答结果中的证据引用对象，不等于 Chunk 本身，但通常由命中的 Chunk / Asset 派生。

#### 8.8.2 最小字段建议
- `id`
- `receipt_id`
- `kb_id`
- `doc_id`
- `title`
- `excerpt`
- `source`
- `preview_locator`
- `score`（可选）

#### 8.8.3 关键要求
Evidence 必须可用于：
- 前端预览；
- Agent 引用；
- 用户回查。

---

## 9. 关键关系模型

### 9.1 核心关系

```text
KnowledgeBase 1 --- n Folder
KnowledgeBase 1 --- n Document
Folder       1 --- n Document
Document     1 --- n Asset
Document     1 --- n Chunk
Asset        1 --- n Chunk
Chunk        1 --- 1 EmbeddingRecord(逻辑上)
IngestionJob 1 --- n Document / Asset / Chunk 结果
Answer       1 --- n Evidence
```

### 9.2 关系解释
- 一个知识库内可以有多级文件夹；
- 文档是用户管理对象；
- 资产是文档内部或独立存在的可引用对象；
- 检索主要命中 Chunk；
- Evidence 是回答阶段对 Chunk / Asset / Document 的引用包装。

## 10. 导入与嵌入总体流程

### 10.1 总体流程图

```text
输入源
→ 来源识别
→ 知识库边界确认
→ 文件夹路径映射
→ 文档对象建立
→ 内容解析
→ 资产抽取
→ 文本化 / OCR / Caption
→ Chunk 切分
→ Embedding
→ 索引写入
→ Receipt 回执
```

### 10.2 为什么要把它看成流程而不是函数调用

因为“上传文件然后索引”只是实现视角。
从产品与系统视角，它其实是：
1. 知识对象生成；
2. 多阶段处理；
3. 多状态回执；
4. 可失败、可补偿、可重试的工作流。

## 11. 各类输入的接入策略

### 11.1 Markdown

#### 11.1.1 Markdown 是主优先对象
因为 Markdown 天然适合作为本地知识源：
- 结构清晰；
- 版本友好；
- 标题层级明显；
- 常常会引用本地图片与相对资源。

#### 11.1.2 Markdown 导入时至少要做 4 件事
1. 解析正文文本；
2. 识别标题层级；
3. 识别本地相对路径图片 / 资源引用；
4. 建立文档与内嵌资产关系。

#### 11.1.3 Markdown 内嵌图片策略
建议分两阶段：

**P0：**
- 先识别图片引用；
- 能定位到本地图片文件；
- 为该图片建立 `Asset` 锚点；
- 若能 OCR，则抽取文本并转成 Chunk；
- 回答中允许引用该 Asset。

**P1：**
- 进一步做图片描述、结构化图示理解、图文联合检索。

#### 11.1.4 相对路径处理原则
- 默认相对于 Markdown 文档所在目录解析；
- 目录导入时优先保留原目录结构；
- 解析失败的资源要进入回执或告警，而不是悄悄忽略。

---

### 11.2 PDF

#### 11.2.1 PDF 是第二主优先对象
PDF 在知识库里会非常常见，尤其是：
- 规范文档；
- 论文；
- 合同/扫描件；
- 输出报告；
- 带图表的材料。

#### 11.2.2 PDF 接入策略
建议同样分层：

**正文层：**
- 优先抽取文字层；
- 文字层质量差时回退 OCR；
- 切分成 Chunk。

**页面资产层：**
- 可按页记录 page locator；
- 对图表、扫描页、页内图片保留 Asset 抽取入口；
- 后续允许页级预览和引用。

#### 11.2.3 P0 重点
P0 不一定要求所有 PDF 图片都被高质量理解，但至少要：
- 有页码定位；
- OCR 可回退；
- 证据可定位到页；
- 为后续页内资产抽取保留对象位置。

---

### 11.3 图片 / 流程图 / 扫描页

#### 11.3.1 设计判断
图片内容不是“特殊附件”，而是潜在知识对象。

#### 11.3.2 P0 推荐策略
图片进入检索时，优先通过**文本化**接入：
- OCR 文本；
- 用户补充说明；
- 基础 caption；
- 周边文档上下文。

#### 11.3.3 为什么 P0 不强推原生图像向量检索
因为当前更重要的是：
- 对象模型先立住；
- 资产能被看见、引用、预览；
- OCR / 文本化结果先能接入主检索链路。

原生图像 embedding 可放到后续阶段。

---

### 11.4 URL / 网页

#### 11.4.1 URL 是补充知识源
URL 导入本质上也应该落到 `Document` 语义，而不是特殊旁路。

#### 11.4.2 最低要求
- 每个 URL 要有独立导入结果；
- 成功、空、失败区分明确；
- 失败不要把整批回执伪装成成功；
- 后续同样可以形成文档对象、Chunk 和 Evidence。

---

### 11.5 目录导入

#### 11.5.1 目录导入是你这个产品的关键能力
因为本地知识库的真实来源往往就是一整个项目目录，而不是一两个手工上传文件。

#### 11.5.2 默认行为
- 目录导入默认保留相对目录树；
- 目录结构映射为知识库内部 Folder 树；
- 文件按相对路径挂入 Folder；
- Markdown 相对资源优先从该目录树中解析。

#### 11.5.3 需要避免的错误做法
- 把所有文件拍平；
- 丢失原始相对路径；
- 只导文本，不记录资源关系；
- 导入成功 / 失败没有逐项回执。

---

## 12. 删除、重导入、重建索引的边界

### 12.1 删除 Document
删除文档是：
- 撤销该文档及相关 Chunk / Asset 的可见性；
- 清理关联索引；
- 同步维护计数与引用。

### 12.2 重导入 Document
重导入是：
- 同一来源文档内容变化后的再处理；
- 可能需要替换旧 Chunk / Asset 结果；
- 需要保留来源身份和历史痕迹。

### 12.3 重建索引
重建索引是：
- 在不改变文档来源身份的前提下，重做切分 / 嵌入 / 索引；
- 更像处理层动作，而不是内容层动作。

### 12.4 为什么要区分这三者
如果不区分，后面会出现：
- 用户以为删文档，实际只删了向量；
- 用户以为重导入，实际生成了重复文档；
- 用户以为重建索引，实际把来源关系搞丢了。

---

## 13. 导入失败与一致性策略

### 13.1 当前最核心的底座要求

系统至少要做到：
1. 导入结果不能“假成功”；
2. `doc_count` 不能按输入数盲增；
3. 单项失败不能污染整批统计；
4. 已落盘但索引失败的文件要有明确处理策略；
5. 删除时要能清理历史脏引用。

### 13.2 推荐的一致性思路

#### 13.2.1 逐项回执
每个文件 / URL 至少区分：
- `indexed`
- `empty`
- `failed`

#### 13.2.2 计数只对有效成功项增加
只有真正产出可索引内容的项才计入成功数与 doc_count。

#### 13.2.3 失败补偿
- 文件已落盘但索引失败：清理文件，或显式标记失败文档；
- URL 抓取失败：记录失败原因，不算成功。

#### 13.2.4 删除脏引用
删除 ref_doc 时要能兼容历史 stale node 引用，而不是直接因 KeyError 等问题失败。

### 13.3 P0 与 P1 的差异

**P0：**
- 先有可靠回执；
- 先做基础补偿；
- 先让系统“知道自己失败了什么”。

**P1：**
- 再做更完整的任务持久化、重试策略、失败文档状态管理。

---

## 14. 检索与证据链路

### 14.1 当前主检索单元
P0 仍以 Chunk 为主检索单元。

### 14.2 Asset 如何进入检索
P0 主要通过以下方式接入：
- OCR 文本切成 Chunk；
- caption 文本切成 Chunk；
- 文档上下文引用；
- Asset 作为 Evidence 被直接引用。

### 14.3 证据必须返回什么
至少返回：
- `kb_id`
- `doc_id`
- `title`
- `excerpt`
- `preview_locator`
- `receipt_id`（如有）

### 14.4 关键产品要求
如果一个图片 / 流程图只是“附在文档里”，但不能：
- 被检索命中；
- 被回答引用；
- 被预览定位；
那么它仍然不算真正进入知识体系。

---

## 15. 范围控制与安全边界

### 15.1 当前已确认口径
- Chat 入口未声明范围：默认拒绝；
- P0 单次 Chat 仅允许显式单知识库；
- 不保留 global compatibility mode。

### 15.2 这对本设计意味着什么
所有知识对象都必须有清晰归属：
- Document 属于哪个 KB；
- Asset 属于哪个 KB / Document；
- Chunk 属于哪个 KB / Document / Asset；
- Evidence 必须可回显其 KB 范围。

### 15.3 Folder 不是安全边界
Folder 可用于组织与收窄，但不能替代 `kb_id` 级范围契约。

### 15.4 当前安全风险必须持续可见
由于当前仍是共享单索引 + 逻辑过滤：
- `storage_mode` 应诚实表达现状；
- 对外接口不要暗示已经是物理隔离；
- 未来 Agent 接入不能建立在“默认相信过滤逻辑永不出错”的前提上。

## 16. 面向 Agent 的扩展设计

### 16.1 为什么这个项目天然适合接 Agent
因为它本质上就是“受控知识底座”，而 Agent 非常需要：
- 明确范围；
- 可检索知识；
- 证据链；
- 文档预览。

### 16.2 后续 Agent 接入应遵守的契约

#### 16.2.1 显式授权范围
Agent 不得默认访问全部知识库。

#### 16.2.2 检索结果必须带证据
Agent 消费的知识不能只有文本片段，还应带：
- `kb_id`
- `doc_id`
- `evidence_id`
- `preview_locator`

#### 16.2.3 与现有自研 Agent 框架的关系
当前建议采用：
- **共存设计**，不是立即替换；
- 先把知识接口做稳；
- 后续无论是自研工具注册体系还是 MCP / 标准工具接口，都可以接到同一知识底座。

### 16.3 对外能力可以拆成哪些工具
后续可演进出：
1. `list_kbs`
2. `search_kb`
3. `preview_document`
4. `list_documents`
5. `get_import_receipt`
6. `reindex_document`
7. `delete_document`

## 19. 总结

这套本地多知识库知识助手的本质，不是“再做一个会聊天的文档问答工具”，而是要搭一个**本地优先、边界明确、证据可追、对象清晰、可扩展到 Agent 的知识底座**。

对于你最关心的“知识库内部要不要有文件夹”，结论很明确：

**要有。**

但要放在正确位置：
- 它是组织结构；
- 不是安全边界；
- 不是知识库的替代；
- 不是物理隔离。

对于 Markdown、PDF、图片、流程图，结论也很明确：

**它们都应该进入同一知识对象体系，只是进入方式不同。**

其中：
- Document 是来源对象；
- Asset 是图像/流程图等知识资产对象；
- Chunk 是当前主检索单位；
- Evidence 是回答阶段的引用对象；
- Receipt / Job 是导入过程的可追踪对象。

只要这套底座立住，后面无论是：
- 多知识库扩展；
- 文件夹树增强；
- 多模态接入；
- 外部 Agent 调用；
- 逻辑隔离演进到物理隔离；
都能沿着统一对象模型继续长，而不是推翻重来。
