# 本地多知识库知识助手平台产品需求文档（PRD）

## 1. 文档信息
- 文档版本：v0.4
- 文档状态：根据评审结果修订稿
- 创建日期：2026-07-22
- 适用范围：本地多知识库知识助手平台的产品定位与需求定义
- 对应目录：`docs/20260722-local-multi-kb-assistant/`
- 当前阶段：Stage 1 / 仅完成 PRD，不展开实施方案、测试方案、测试报告

## 2. 本轮 PRD 的目的
本轮 PRD 只解决一件事：**先把这个项目到底要做成什么产品讲清楚。**

当前不进入技术实现、排期拆解、测试设计等阶段，而是优先回答以下问题：
1. 这个项目的产品定位是什么。
2. 这个项目服务哪些用户。
3. 这个项目优先解决哪些核心问题。
4. 这个项目的信息架构和核心对象应该如何设计。
5. 这个项目如何从一开始就具备可扩展性，方便未来接入更多知识形态和更多 Agent 系统。
6. 当前代码现实与目标产品之间的架构差距到底在哪里。

## 3. 项目背景与问题定义

### 3.1 当前项目现状
结合当前仓库现状，可以确认本项目已经具备若干基础能力，但必须准确描述其边界：

1. **已具备本地知识导入、索引、检索、问答的基本链路。** 项目已经具备从本地文件进入索引、检索到回答生成的可运行闭环。
2. **已具备基于 metadata 标签的逻辑多知识库能力（共享单一索引，按 `kb_id` 过滤）。** 当前 `storage/` 下仍是全局共享的 `docstore.json`、`index_store.json`、`default__vector_store.json`、`image__vector_store.json` 等核心存储文件；知识库范围控制主要依赖节点 `metadata["kb_id"]` 的检索过滤，尚未实现存储级隔离或独立命名空间隔离，跨库边界目前依赖过滤逻辑正确性。
3. **已具备 PDF 文字层读取与 OCR 回退能力。** 说明项目天然适合处理不完全标准化的本地文档资料，而不仅限于纯文本 Markdown。
4. **当前存在双轨前端现实。** 一方面已有 `FastAPI + React + Electron` 的本地桌面产品主线骨架；另一方面仓库中仍保留 `app.py + frontend/*.py` 形式的遗留 Streamlit Demo。对当前 PRD 而言，前者视为主线，后者应视为遗留兼容资产，而非未来主产品方向。
5. **已具备自研 Agent 雏形。** 当前已有自研的 plan-executor、tool routing、`risk_level` 分类、审批与回执链路，说明系统具备向“知识能力底座”演进的空间；但这与未来 MCP / 标准工具接口仍不是同一层面的稳定对外契约。

### 3.2 当前核心问题
虽然项目已有基础，但产品层仍存在明显未收口的问题：

1. 当前叙事仍容易在“本地 RAG 工具”“桌面 Agent”“知识平台”之间摇摆。
2. 多知识库已从“共享索引 + metadata 过滤”升级为物理索引隔离：`default` 兼容 `storage/`，其他知识库使用 `storage/kbs/{kb_id}/`；历史共享索引中的非 default 数据需要重新导入或重建后进入新目录。
3. 当前多知识库边界依赖过滤逻辑正确性；一旦过滤失效，存在跨库检索、跨库引用和数据泄露风险。特别是在未来开放给外部 Agent 或集成方时，这会直接升级为越权访问风险，而不只是检索精度问题。
4. 项目目前对 Markdown 与 PDF 较友好，但对图片、流程图、截图、扫描页等内容的产品定义还不够完整，容易继续退回“附件模式”。
5. 新桌面主线已有雏形，但信息架构、导航结构、对象边界、范围控制契约尚未完全固化。
6. 未来若要接入其他 Agent 项目，目前仍缺少清晰的产品级接口边界与长期兼容策略。
7. 遗留 Streamlit 入口如果不在产品文档中明确归宿，会继续强化“这是 Demo 还是平台”的认知混乱。

### 3.3 本轮必须先定下来的判断
本轮 PRD 需要先做出以下关键判断：
- 我们不是继续做一个“能聊天的知识库 Demo”。
- 我们也不是现在就做一个“全能自治 Agent 平台”。
- 我们要做的是：**本地优先、多知识库、证据优先、多模态、可被 Agent 调用的知识助手平台。**

### 3.4 现状与目标之间的关键架构差距
这次 PRD 必须明确：

**从当前系统到目标产品，不是“细节待完善”，而是从“过滤标签型逻辑多库”向“知识库一等对象 + 隔离边界可演进”的架构升级。**

这意味着：
1. 8.2 节“知识库是一等对象”描述的是**目标态原则**，不是对当前实现现状的背书。
2. ER-04 “存储边界扩展能力”不是普通增强项，而是当前安全边界和产品可信度的收敛方向。
3. FR-07 / ER-05 一旦开放给外部 Agent，知识范围控制就不再只是检索精度问题，而是越权访问风险问题。

## 4. 产品定位

### 4.1 一句话定位
本产品定位为：**本地优先的多知识库知识助手平台。**

### 4.2 产品本质
它的本质不是一个聊天框，而是一个围绕“知识库”组织、沉淀、检索、引用和复用本地知识的工作平台。

它首先服务人类用户，其次服务 Agent；
它先把知识底座做好，再逐步开放给更多自动化系统使用。

### 4.3 产品角色定义
当前与中期看，本产品承担三层角色：

#### 角色一：本地知识助手
帮助用户把散落在本地文件系统中的文档、手册、方案、记录和资料，转化为可回答、可追溯、可复用的知识对象。

#### 角色二：多知识库工作台
帮助用户按项目、主题、客户、场景组织知识边界，而不是把所有资料堆进同一个索引里混合使用。

#### 角色三：Agent-ready 的知识底座
未来对外提供可控的知识接入能力，让其他 Agent、自动化流程或插件在受限范围内使用知识库，而不是默认拿到全量上下文。

### 4.4 产品愿景
构建一个真正适合长期沉淀本地知识的基础平台：
- 对个人用户，它是可信、可证据化的本地知识助手；
- 对项目团队，它是可管理边界的知识工作台；
- 对未来生态，它是可被接入的知识能力底座。

### 4.5 非目标与避免误解
当前阶段明确不把本产品定义为：
1. 单纯聊天 UI 的 RAG Demo；
2. 以“自动执行任务”为主目标的桌面自治 Agent；
3. 云端协同知识平台；
4. 企业级多租户权限系统。

### 4.6 当前阶段的产品边界
当前阶段聚焦“知识底座成立”这件事，即：
- 知识库对象清晰；
- 文档与资产对象清晰；
- 检索与证据链清晰；
- 范围控制契约清晰；
- 接口扩展方向清晰。

## 5. 目标用户

### 5.1 用户类型 A：个人知识工作者
典型包括研发、产品、咨询、研究、运营等重度文档用户。

他们的问题不是“没有 AI”，而是“资料很多，但找不到、连不起来、也不敢信回答依据”。

### 5.2 用户类型 B：项目型知识管理者
典型包括长期维护多个项目、客户、课题、代码库或研究方向的人。

他们真正需要的是：
- 一份资料属于哪个知识边界；
- 问答时到底引用了哪个知识库；
- 不同知识库之间能否明确区分、比较和复用。

### 5.3 用户类型 C：Agent 构建者 / 自动化开发者
典型包括要把知识能力嵌入现有 Agent、工作流、插件、自动化脚本中的开发者。

他们最关心的是：
- 是否存在稳定对象模型；
- 是否能按知识范围调用；
- 是否能拿到证据与来源；
- 是否能逐步接入而不是一次性重写。

## 6. 核心用户问题与使用场景

### 6.1 核心用户问题
本产品优先解决以下问题：
1. 本地资料来源复杂，难统一导入与使用。
2. 多项目 / 多主题资料混在一起，边界不清。
3. Markdown、PDF、截图、流程图、扫描页等内容价值高，但常被忽略或降级为附件。
4. 回答缺少证据、来源与定位，用户难以信任。
5. 想让 Agent 使用知识时，缺少清晰且安全的范围控制方式。

### 6.2 核心场景
1. 用户按项目创建多个知识库，分别导入 Markdown、PDF 与相关图片资料。
2. 用户在单个知识库内提问，获得带证据、可预览、可定位的回答。
3. 用户从一篇文档中的流程图或截图，直接命中相关资产并追溯其宿主文档。
4. 外部 Agent / 集成方只被授予某几个知识库范围，在受限边界内进行检索、问答或引用。

### 6.3 首批高频任务示例
- “只在《客户 A 方案库》里回答，不要引用其他项目资料。”
- “帮我找这张流程图最可能对应的实施步骤和出处。”
- “这段结论来自哪个 PDF 的哪一页？”
- “让外部 Agent 只能访问《产品文档库》和《FAQ 库》，不能默认访问全部资料。”

## 7. 产品核心价值主张

### 7.1 对最终用户的价值
1. **更清晰的边界**：知识库不是一个过滤标签，而是用户可理解、可管理的工作对象。
2. **更可信的回答**：回答必须附证据、来源与定位信息。
3. **更完整的知识覆盖**：不仅理解 Markdown / PDF 文本，也把图像类资产纳入知识对象体系。
4. **更适合长期积累**：多知识库结构更符合真实工作的长期组织方式。

### 7.2 对开发者 / Agent 系统的价值
1. 提供稳定的知识对象模型与范围控制模型。
2. 提供证据化输出，而不是黑盒回答。
3. 允许未来同时兼容自研 Agent 运行时与标准化外部接口。
4. 为后续插件化、自动化、Agent 化留出清晰接口层。

## 8. 产品原则

### 8.1 本地优先原则
知识导入、索引、检索和使用，默认围绕本地环境构建。

### 8.2 多知识库优先原则
知识库是一级产品对象，不是过滤条件附属字段。

**补充说明：这是一条目标态原则，不代表当前代码已经实现了存储级隔离。** 当前实现仍处于“逻辑多知识库”阶段。

### 8.3 证据优先原则
所有关键回答都应尽可能提供引用来源、片段定位和预览入口。

### 8.4 多模态知识原则
图片、流程图、截图、扫描页等资产不是附件，而是知识的一部分；当它们承载信息时，应具备独立对象身份。

### 8.5 Agent-ready 原则
产品先服务人，再开放给 Agent；但从第一天起就保留清晰的范围控制与接口边界。

### 8.6 可扩展优先原则
导入源、解析器、索引策略、检索链路、前端壳、外部接口都应允许替换或增量扩展，而不破坏核心对象模型。

## 9. 信息架构

### 9.1 一级信息架构
建议一级信息架构围绕以下对象组织：
1. 知识库（Knowledge Base）
2. 文档（Document）
3. 资产（Asset）
4. 问答会话（Session）
5. 引用与证据（Evidence）
6. 外部接入主体 / 集成方（Integration Principal）

### 9.2 核心对象模型

#### 知识库（Knowledge Base）
- 表示一个明确的知识边界与管理单元；
- 持有名称、描述、范围、统计信息、接入策略等元数据；
- 面向用户与外部系统都应可被明确选择。

#### 文档（Document）
- 表示一个导入后的知识来源单元；
- 支持 Markdown、PDF 及后续扩展格式；
- 保留来源路径、导入时间、解析状态、所属知识库等信息。

#### 资产（Asset）
- 表示文档中的图片、流程图、截图、扫描页、附件图像等非纯文本内容；
- 可以从宿主文档派生，也可以在产品层独立展示、检索、引用；
- 必须保留与宿主文档、页码 / 片段 / 位置之间的关系。

#### 问答会话（Session）
- 表示围绕某次知识查询产生的上下文记录；
- 包含问题、检索范围、回答、引用证据与操作历史。

#### 引用与证据（Evidence）
- 表示支撑回答的片段、页码、图像区域、来源文档等信息；
- 是“可相信回答”的关键对象，不是渲染附属品。

#### 外部接入主体（Integration Principal）
- 表示一个外部 Agent、插件、自动化脚本或本地流程；
- 不等同于“多用户系统中的用户账号”；
- 其核心能力是被授予可访问的知识库范围，而不是拥有完整用户权限体系。

### 9.3 对象关系原则
1. 文档必须属于某个知识库。
2. 资产必须能回溯到宿主文档或明确来源。
3. 会话必须显式记录检索范围。
4. 回答必须关联证据。
5. Integration Principal 的访问范围必须显式配置，不能默认继承全量知识范围。

### 9.4 典型导航结构
建议产品主导航优先围绕以下结构展开：
- 首页 / 最近使用
- 知识库列表
- 知识库详情
  - 文档
  - 资产
  - 问答
  - 设置 / 接入
- 全局检索（后续增强）
- 外部接入管理（后续增强）

### 9.5 主用户路径

#### 路径 A：知识沉淀
创建知识库 → 导入文档 / 资产 → 查看解析状态 → 浏览文档 / 资产。

#### 路径 B：知识问答
进入某个知识库 → 明确当前范围 → 提问 → 查看回答 → 查看证据与预览 → 回溯文档 / 资产来源。

#### 路径 C：Agent 接入
创建 / 配置 Integration Principal → 绑定可访问知识库范围 → 调用检索 / 问答接口 → 返回带证据结果。

### 9.6 分层产品视图（为扩展预留）
建议从产品架构上分成四层：
1. **对象层**：知识库、文档、资产、证据、会话。
2. **处理层**：导入、解析、切分、索引、检索、回答生成。
3. **体验层**：桌面端 UI、预览、引用展示、范围选择。
4. **开放层**：本地 API、自研 Agent 接入、MCP / 标准接口包装层。

其中，对象层应尽量稳定；处理层、体验层、开放层允许逐步替换或升级。

## 10. 范围定义

### 10.1 首阶段默认假设
1. 当前阶段以本地单机使用为主，不展开云端协作与团队权限体系。
2. 当前阶段优先验证“知识底座是否成立”，而不是追求复杂 Agent 编排能力。
3. 当前阶段默认主线产品壳为 Electron 桌面端；遗留 Streamlit 仅作为兼容 / 参考资产，不作为未来主线继续扩展。

### 10.1.1 权限边界说明
本 PRD 需要明确区分两类边界：

1. **Out of Scope：多用户身份与组织级权限系统**
   - 不在当前阶段建设账号体系、团队角色、组织权限、租户隔离、审计后台等企业级能力。

2. **In Scope：知识库级范围控制**
   - 面向本地接入方、外部 Agent、插件或自动化脚本，必须能够配置其可访问的知识库范围；
   - 不能默认全量可见；
   - 范围控制是知识平台的核心契约，不等于完整多用户权限系统。

### 10.2 In Scope

#### P0：用于验证产品定位是否成立的最小必要集合
1. **知识库作为用户可理解的管理对象**：支持创建、查看、选择知识库，并在问答前明确当前知识范围。
2. **本地导入与基础解析链路**：支持本地文件导入，首批覆盖 Markdown、PDF，并保留图片 / 页码 / 来源等基础信息。
3. **资产对象纳入知识模型**：图片、流程图、截图、扫描页等资产在数据模型和界面中拥有独立身份，而不是仅做附件占位。
4. **单知识库检索问答**：先在明确单一知识库范围内完成检索、回答和证据输出闭环。
5. **证据与预览能力**：回答能回溯到文档片段、页码、资产或宿主来源，并支持预览。
6. **知识库级范围控制契约**：为外部 Agent / 集成方预留稳定接入边界，至少支持“显式允许哪些知识库可访问”的产品级约束。

#### P1：增强能力
1. 跨知识库检索、比较与汇总问答。
2. 更完整的资产提取、独立浏览、分类与批量管理能力。
3. 更丰富的导入源与解析器扩展。
4. 外部 Agent / 插件的实用化接入能力。
5. 知识库内更细粒度的组织视图，如文件夹、标签、专题视图等。

#### P2：平台化能力
1. 从逻辑多知识库向物理隔离 / 独立命名空间演进。
2. 更标准化的开放接口层（如 MCP / 标准工具协议包装）。
3. 同步、版本、备份、迁移和生态插件体系。
4. 更复杂的自动化编排与多 Agent 协作能力。

### 10.3 Out of Scope
当前阶段明确不纳入：
1. 企业级多用户账号、角色、组织与租户权限体系。
2. 云端协作、远程共享、在线同步。
3. 通用自治执行型 Agent 平台能力。
4. 复杂工作流编排器。
5. 一次性覆盖所有文件格式与企业知识源。
6. 彻底替换遗留 Streamlit 的迁移实施细节。

## 11. 功能需求

### FR-01 知识库管理
产品应支持用户创建、查看、选择和管理多个知识库，并在核心操作中显式体现当前知识范围。

#### 验收口径
1. 用户能创建多个知识库并查看基础元信息。
2. 用户在问答前能明确当前选中的知识库范围。
3. 用户能感知“当前回答来自哪个知识库”，避免范围混淆。
4. PRD / FRD 中必须把“知识库”为一级对象，而非仅作为过滤参数出现。

### FR-02 文档导入与解析
产品应支持本地文档导入，并形成统一的文档对象模型。

#### 验收口径
1. 首阶段至少覆盖 Markdown、PDF。
2. 文档对象保留来源路径、导入时间、所属知识库、解析状态等基础字段。
3. PDF 类文档应支持文字层提取，并允许 OCR 类能力作为补充路径。
4. 后续扩展新格式时，不应破坏既有对象模型。

### FR-03 多模态资产建模
产品应把图片、流程图、截图、扫描页等内容纳入知识模型，而不是仅作为宿主文档附件处理。

#### 验收口径
1. 资产拥有独立标识、来源信息、宿主关系与定位信息。
2. 资产可被预览、引用和回溯。
3. 资产可参与检索结果组织，而不仅在宿主文档详情页中被动展示。
4. **至少在产品定义上，资产应能脱离宿主文档独立被检索命中或被回答结果直接引用。**

### FR-04 检索与问答
产品应提供围绕明确知识范围的检索与问答能力。

#### 验收口径
1. P0 默认支持单知识库范围内的检索与问答闭环。
2. 回答过程必须显式绑定检索范围。
3. 回答结果应能关联证据与来源。
4. 跨知识库检索与比较能力属于 P1 增强项，不作为当前阶段最小闭环前提。

### FR-05 证据与预览
产品应把“回答可信”建立在证据与预览能力之上，而不是只返回自然语言结论。

#### 验收口径
1. 回答结果至少应展示来源文档、片段、页码、宿主资产或其他定位信息中的一部分。
2. 用户应能从回答跳转或展开查看原始证据。
3. 证据展示能力应适用于文本片段与资产对象两类来源。

### FR-06 二级组织能力
产品应允许用户在知识库之上继续组织知识内容，但不要求首阶段一次做深。

#### 验收口径
1. 至少预留文件夹、标签、专题等二级组织能力的扩展位置。
2. 二级组织能力不能破坏“知识库作为第一边界”的原则。
3. 首阶段允许只做最小结构或在 FRD 中先定义扩展位。

### FR-07 Agent 接入能力
产品应为外部 Agent / 集成方提供可扩展的知识接入能力，但必须建立在明确范围控制之上。

#### 验收口径
1. 外部接入主体必须以显式配置的方式绑定可访问知识库范围。
2. 系统不能默认允许外部接入主体访问全部知识库。
3. 返回结果应尽可能保持证据化输出，而不是仅提供黑盒答案。
4. 范围控制失效应被视为安全边界问题，而不只是“召回偏差”。

## 12. 扩展性需求（核心章节）

### ER-01 数据源扩展能力
产品应允许后续扩展更多本地或半本地数据源，而不破坏知识对象模型。

### ER-02 解析器扩展能力
产品应允许按文件类型、内容形态和质量情况扩展解析器，例如 OCR、图像理解、结构化抽取等。

### ER-03 检索链路扩展能力
产品应允许替换或组合不同检索策略，包括全文、向量、混合检索、资产检索等。

### ER-04 存储边界扩展能力
产品必须支持从“共享存储上的逻辑多知识库”演进到“知识库级物理隔离或独立命名空间”。

这不是普通优化项，而是架构级演进方向，原因包括：
1. 当前状态仍依赖过滤逻辑维持跨库边界；
2. 一旦要对外开放受限访问，这种边界会成为实际安全风险；
3. 产品可信度要求知识边界能持续演进到更强隔离形态。

### ER-05 接口开放扩展能力
产品应允许未来同时兼容两类开放方式：
1. **现有自研接入方式**：基于当前自研 Agent runtime / tool registry / approval 机制继续演进；
2. **标准化开放方式**：在外层增加 MCP 或其他标准接口包装。

当前 PRD 默认按**共存设计**处理，而不是预设必须替换现有自研框架。具体替换、包装或双栈策略，留待 FRD 再收敛。

### ER-06 版本演进与迁移能力
随着对象模型、隔离边界、开放接口不断演进，产品应具备向后迁移、升级和兼容的能力，避免让已有知识资产失效。

## 13. 非功能需求

### NFR-01 可理解性
用户应能理解“当前在哪个知识库内操作、回答引用了什么、资产与文档的关系是什么”。

### NFR-02 可维护性
对象模型、处理链路、界面层、开放层应有清晰分层，避免产品能力演进时互相耦合。

### NFR-03 可扩展性
新增格式、解析器、检索方式、外部接口时，不应频繁推翻知识对象层。

### NFR-04 本地可用性
核心导入、检索、问答链路应可在本地环境独立完成。

### NFR-05 可观察性
应能识别导入状态、解析状态、索引状态、检索范围和引用来源，便于后续问题定位。

### NFR-06 安全边界
必须明确把“知识范围控制”视作安全边界的一部分。

当前已知现实是：多知识库主要依赖 `kb_id` 过滤维持边界，因此：
1. 过滤失效不只是结果不准，而可能导致跨库数据泄露；
2. 对外开放给 Agent / integration principal 后，过滤失效会直接演变为越权访问；
3. 后续设计应优先收敛“范围控制契约”和“隔离边界演进路径”。

## 14. 产品级成功标准

### 14.1 北极星方向
用户愿意把它当作长期管理本地知识边界与证据化问答的基础平台，而不是一次性的 RAG Demo。

### 14.2 当前阶段成功标准
1. 用户能清晰创建和管理多个知识库。
2. 用户能在明确范围内完成单知识库问答，并看到证据与预览。
3. 资产对象不再只是附件，而能在产品中被明确建模和引用。
4. 外部接入方向具备清晰的范围控制契约。
5. PRD 能真实反映当前架构差距，而不是高估现状成熟度。

## 15. 原始阶段暂不拍板的事项（已由 2026-08-17 能力更新部分取代）
1. 知识库是否在下一阶段直接引入物理隔离，还是先定义命名空间抽象。
2. 资产对象首阶段做到何种识别粒度。
3. 外部开放层先做本地 API、工具协议包装，还是两者并行。
4. 遗留 Streamlit Demo 的具体退场或兼容策略。

## 16. PRD 结论
本轮 PRD 收口后的核心结论如下：

1. 产品定位：本地优先、多知识库、证据优先、多模态、Agent-ready 的知识助手平台。
2. 原始立项现实（2026-07）：项目已有本地导入、索引、检索、问答与自研 Agent 雏形，但当时多知识库仍是共享单索引上的逻辑隔离；2026-08-17 已完成物理索引隔离。
3. 当前核心差距：物理索引边界已经落地，后续重点转向历史数据迁移、权限模型和标准化开放层。
4. 范围收口：P0 只验证知识底座是否成立，不把首版扩成完整平台。
5. 扩展原则：为多源、多模态、多检索、多接入保留稳定边界。
6. 风险判断：把多知识库过滤失效明确提升为安全边界问题。

## 2026-08-17 能力更新

1. **物理隔离**：非 default 知识库必须使用独立 `StorageContext` 和持久化文件集，API 回显 `isolation_level=physical_isolated`。
2. **Embedding 缓存恢复**：当本地缓存缺失且运行时远程下载关闭时，前端必须提供 ModelScope 白名单恢复按钮，显示下载中、失败可重试和成功后重新预热状态。
3. **OCR 版面质量**：OCR 必须优先利用 `rec_boxes` / `dt_polys` 恢复阅读顺序；扫描 PDF 保留页标记；规则表格可恢复为 Markdown 表格并输出行列、置信度等诊断。
4. **发布边界**：证书、签名和公证暂不阻塞上述本地功能开发，但未完成这些外部门禁时不得宣称正式 macOS 发布完成。
