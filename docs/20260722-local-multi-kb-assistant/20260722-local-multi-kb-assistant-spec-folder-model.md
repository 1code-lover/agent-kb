---

## 2. 结论先行

### 2.1 一句话结论
**知识库内部应该支持文件夹，但文件夹是组织对象，不是安全边界对象；真正的一等边界仍然是知识库。**

### 2.2 本文坚持的四个判断
1. **KnowledgeBase 是范围边界对象。**
2. **Folder 是组织对象，不是 mini-KB。**
3. **Document / Asset 是用户可感知的一等知识对象。**
4. **Chunk / OCR Text / Derived Nodes 是系统内部派生对象。**

### 2.3 用户心智
- 用户先选知识库，再进入文件夹，再查看文档或资产。
- 问答默认面向知识库范围，文件夹只做 KB 内部的局部收窄。
- 被检索、被引用、被预览的主对象是 Document / Asset，而不是 Folder 本身。

---

## 3. 为什么要支持文件夹

### 3.1 文件夹解决的是真实资料组织问题
本地知识库的来源通常是项目目录、笔记目录、团队资料包，而不是几个彼此孤立的上传文件。
如果系统只支持“知识库 + 平铺文件”，会直接丢掉用户原本的目录语义：
- 项目 / 模块 / 子系统的层级关系；
- Markdown 相对路径资源的来源上下文；
- 同名文件在不同目录下的区分能力；
- 浏览、排查、重导入时的定位能力。

### 3.2 但文件夹不应该承担边界职责
文件夹可以有，而且应该有；但它的职责应该稳定在：
- 目录组织；
- 导入映射；
- 浏览导航；
- 检索收窄辅助；
- 来源表达与证据回显。

文件夹不应该被设计成：
- 主权限边界；
- 主隔离边界；
- 主存储边界；
- 可替代 `kb_id` 的授权对象。

---

## 4. 对象层级与职责划分

### 4.1 推荐层级
```text
KnowledgeBase
└─ Folder（可嵌套）
   └─ Document
      └─ Asset
         └─ Chunk / OCR Text / Derived Nodes
```

### 4.2 各对象角色

#### KnowledgeBase
- 问答范围边界；
- Agent 授权边界；
- 原始资料归属边界；
- 后续物理隔离与独立存储的演进锚点。

#### Folder
- 表达目录树；
- 承接目录导入映射；
- 支撑浏览、过滤、来源展示；
- 为文档和资产提供稳定的路径上下文。

#### Document
- 表达 Markdown / PDF / 文本等来源文档；
- 作为预览、引用、回溯的主来源对象；
- 可以属于某个 Folder，也可以直接挂在 KB 根层。

#### Asset
- 表达文档内嵌图片、独立图片、流程图截图、扫描件等资产；
- 可以独立被预览、被 OCR、被证据引用；
- 与宿主 Document 保持关联，但不再被视为“附件黑盒”。

#### Chunk / OCR Text / Derived Nodes
- 是检索、召回、排序用的内部处理对象；
- 可以来源于 Document 正文、PDF OCR、图片 OCR 等；
- 不应替代用户对 Document / Asset 的主心智。

---

## 5. Folder 的最小对象模型

### 5.1 定义
Folder 是知识库内部的组织目录对象，用于表达层级结构、来源路径与浏览语义。

### 5.2 最小字段建议
- `folder_id`
- `kb_id`
- `parent_folder_id`
- `name`
- `path`
- `source_path`（本地目录导入时可选）
- `created_at`
- `updated_at`

### 5.3 关键约束
- Folder 必须从属于某个 `kb_id`；
- Folder 可以嵌套；
- Folder 不能跨知识库移动；
- Folder 不是授权边界对象；
- Folder filter 不能脱离 `kb_id` 单独生效。

### 5.4 当前阶段的务实做法
如果这一阶段还没有很强的目录重命名 / 移动 / 缓存需求，可以先让 `folder_path + source_rel_path` 支撑主流能力。
`folder_id` 仍然建议预留，但不应成为 P0 / P1 的强依赖前提。

---

## 6. 导入与 Folder 映射规则

### 6.1 目录导入
目录导入是这个产品的关键能力，因为真实用户往往是把一整个知识目录纳入 KB，而不是零散上传若干文件。

建议默认行为：
- 目录导入默认保留相对目录树；
- 目录结构映射为知识库内部 Folder 树；
- 文件按相对路径挂入对应 Folder；
- Markdown 相对资源优先从该目录树中解析；
- 导入回执应明确哪些文件、图片、OCR 结果挂载到了哪个路径。

### 6.2 单文件导入
- 单文件导入也必须先声明 `kb_id`；
- 文件可以直接挂到 KB 根目录；
- 也可以显式指定 `folder_path` 作为落点；
- 后续重导入时应尽量保持来源路径稳定。

### 6.3 Markdown 资源继承规则
- Markdown 内嵌资源默认继承宿主文档的 `kb_id`；
- 默认继承宿主文档的 Folder 语义；
- 若图片被单独抽取为 Asset，仍需保留其宿主文档与所在路径信息；
- 资源解析失败不应导致整个文档直接失踪，至少要在回执中显式暴露失败项。

---

## 7. 图片、OCR 与 Folder 的协同

### 7.1 当前建议的产品策略
这一阶段优先支持：
1. 图片作为 Asset 入库；
2. OCR 成功则生成可检索文本；
3. OCR 文本进入索引；
4. 命中 OCR 文本时回指原始图片 Asset；
5. OCR 失败不等于导入失败。

### 7.2 Folder 在图片链路中的价值
Folder 不是图像理解能力本身，但它决定了图片被如何组织与回指：
- 图片来自哪个知识库；
- 位于哪个目录；
- 属于哪个文档；
- 在预览与证据中如何表达来源。

对于流程图截图、扫描件、文档插图，这一点尤其重要：
即使当前只做 OCR，不做复杂图像理解，也要保证命中后用户能知道“这张图来自哪个 KB / 哪个 Folder / 哪个 Document”。

---

## 8. 检索、问答与安全边界

### 8.1 当前必须坚守的规则
1. 未声明 KB 范围 = 默认拒绝。
2. Folder filter 只能在已授权 KB 内部生效。
3. 不能用 Folder 去替代 `kb_id` 契约。
4. 证据回显需要让用户知道来自哪个 KB、哪个 Folder、哪个 Document / Asset。

### 8.2 为什么这里必须说得更重
当前系统现状仍是共享单索引 + 逻辑过滤，因此：
- `storage_mode` 应诚实表达现状；
- 对外接口不能暗示已经具备物理隔离；
- 未来 Agent 接入不能建立在“默认相信过滤逻辑永不出错”的前提上。

换句话说，Folder 的引入绝不能稀释 KnowledgeBase 作为边界对象的地位。

### 8.3 对 Agent 接入的含义
- 外部 Agent 的最小授权单位仍应是 KnowledgeBase；
- Folder 只作为 KB 内部附加收窄能力；
- 不能用“授权若干 Folder”来替代“声明被授权的 KB 范围”；
- 如果未来支持更细粒度授权，也应建立在 KB 已显式声明的前提上。

---

## 9. 前后端表达建议

### 9.1 前端信息架构
推荐主导航心智保持为：
1. 先看知识库列表；
2. 进入单个知识库；
3. 在知识库内浏览 Folder 树；
4. 查看 Document / Asset；
5. 在问答中附加 Folder 级收窄条件。

### 9.2 证据与预览表达
Evidence 和预览面板建议稳定回显以下信息：
- `kb_name` / `kb_id`
- `folder_path`
- `document_title` 或 `asset_name`
- 页码、锚点、图片定位或预览定位信息

这样用户才能真正把“命中的一段文本”重新映射回原始资料结构。

---

## 10. 分阶段落地建议

### 10.1 P0 / P1 优先事项
本轮最值得先做的事：
1. 文档 / 资产稳定保存 `folder_path` 和 `source_rel_path`；
2. 让 Evidence 和预览稳定回显 Folder 路径；
3. 让 Markdown 内嵌资产与图片 OCR 命中能回指到所在 Folder；
4. 让 KB -> Folder -> Document / Asset 的对象心智在前后端表达一致。

### 10.2 P2 以后再考虑的增强项
- Folder 树完整落模与更强移动 / 重命名能力；
- Asset 独立命中后的更强预览与定位；
- 跨库比较 / 聚合检索；
- 与物理隔离演进协同的更稳定对象标识；
- 是否需要更细粒度、但仍以 KB 为前提的授权增强。

---

## 11. 最终建议

对这个项目来说，Folder 最合适的设计不是做重，而是做稳：

1. **先把 Folder 作为 KB 内的稳定组织层建起来；**
2. **先把导入、检索、证据、预览、OCR 与 Folder 打通；**
3. **先坚持 KB 边界优先，Folder 只做收窄与表达；**
4. **等 KB 边界、导入诊断、资产闭环都稳了，再决定 Folder 是否需要更强对象能力。**

这样做的好处是：既不和当前共享索引的现实冲突，也不和后续物理隔离升级打架，同时还能与图片资产、OCR、Agent 接入方向保持兼容。
