# 本地多知识库知识助手平台功能设计文档（FRD）

## 1. 文档信息
- 文档版本：v0.1
- 文档状态：基于 PRD v0.4 的首版设计稿
- 创建日期：2026-07-22
- 对应 PRD：`docs/20260722-local-multi-kb-assistant/20260722-local-multi-kb-assistant-prd.md`
- 对应目录：`docs/20260722-local-multi-kb-assistant/`
- 当前阶段：Stage 1 / 功能设计，不展开实施方案与测试方案

## 2. 文档目的
本 FRD 用来回答下面五个问题：
1. PRD 里的产品定位，具体落成哪些功能模块。
2. “知识库是一等对象”在产品设计上到底意味着什么。
3. 资产为什么不是附件，它在对象模型和交互模型里如何体现。
4. 范围控制契约如何设计，才能支撑未来 Agent 接入，又不掩盖当前逻辑隔离的风险。
5. 现有 Electron 主线、自研 Agent 雏形、遗留 Streamlit Demo 在产品设计上如何被统一描述。

## 3. 设计输入与边界

### 3.1 已确认的上位输入
本 FRD 直接继承以下 PRD 判断：
1. 产品定位是“本地优先、多知识库、证据优先、多模态、Agent-ready 的知识助手平台”。
2. 当前多知识库现实仍是共享单索引上的 `kb_id` 逻辑过滤，不是物理隔离。
3. “知识库是一等对象”是目标态产品原则，不代表当前实现已达成。
4. P0 目标是验证知识底座是否成立，不做成完整平台首版。

### 3.2 本 FRD 不解决的问题
当前 FRD 不展开：
1. 具体数据库 / 向量库 / 文件存储选型；
2. API 路由、参数字段、SDK 细节；
3. 代码层类图、表结构、目录改造计划；
4. 测试命令、覆盖率目标与执行报告；
5. 企业级多用户与租户体系。

## 4. 总体功能设计结论

### 4.1 P0 阶段的核心产品闭环
P0 阶段要证明的不是“系统已经完全安全可开放”，而是以下闭环已经成立：

1. 用户能创建和管理多个知识库。
2. 用户能把 Markdown / PDF / 图片相关资产导入到明确知识边界中。
3. 系统能把文档与资产作为对象组织起来，而不是只做文件堆积。
4. 用户能在单知识库范围内完成问答，并看到证据与预览。
5. 系统已形成清晰的范围控制契约，为后续 Agent 接入预留稳定边界。

### 4.2 P0 的关键设计态度
P0 阶段必须承认：
- 当前边界主要仍依赖逻辑过滤；
- 因此 P0 可以设计“范围控制契约”，但**不能把自己描述成已经具备高强度外部安全隔离的平台**；
- “可接入”与“可安全大规模开放”不是同一件事。

### 4.3 P0 / P1 / P2 设计分层结论
1. **P0**：建立对象、范围、证据、资产、单库问答闭环。
2. **P1**：增强跨库能力、外部实用化接入、资产深度能力。
3. **P2**：完成从逻辑隔离向物理隔离 / 标准化开放层的架构升级。

## 5. 核心模块设计

### 5.1 模块 M1：知识库边界模型

#### 5.1.1 设计目标
把“知识库”从标签概念提升为用户和系统都能理解的一级对象。

#### 5.1.2 功能定义
知识库模块负责：
1. 创建、查看、编辑、归档知识库；
2. 展示知识库基础信息，如名称、描述、文档数、资产数、最近导入时间、最近问答时间；
3. 作为文档、资产、会话、范围控制的统一归属边界；
4. 作为问答前的显式范围选择对象；
5. 作为对外接入授权的最小范围单元。

#### 5.1.3 关键产品约束
1. 文档必须属于一个知识库。
2. 资产必须能追溯到某个知识库。
3. 会话必须记录当次知识库范围。
4. 对外接入授权不能绕过知识库对象直接面向底层索引。
5. 在产品表达上，知识库不应被弱化成一个隐藏过滤参数。

#### 5.1.4 用户可见形态
建议在产品中为知识库提供：
- 列表页；
- 详情页；
- 基础统计卡片；
- 范围切换器；
- 接入 / 权限页签。

#### 5.1.5 P0 验收判断
P0 验收关注的是“知识库是否已成为稳定的产品对象”，而不是“是否已经物理隔离”。

### 5.2 模块 M2：文档导入与解析模型

#### 5.2.1 设计目标
把本地文件导入流程从“上传动作”设计为“知识对象生成流程”。

#### 5.2.2 功能定义
文档导入模块负责：
1. 选择目标知识库后导入本地文件；
2. 识别文件类型并进入对应解析路径；
3. 记录来源路径、导入批次、解析状态、失败原因；
4. 为后续切分、索引、证据定位提供原始来源基础。

#### 5.2.3 首阶段支持范围
P0 首批支持：
1. Markdown；
2. PDF；
3. 可从文档中发现或派生的图片类资产；
4. 与 PDF 页码、Markdown 段落、宿主位置相关的定位信息。

#### 5.2.4 关键状态设计
建议至少存在以下状态：
- 待导入；
- 导入中；
- 已解析；
- 部分解析成功；
- 解析失败；
- 已索引；
- 已禁用 / 已归档。

#### 5.2.5 失败与回退设计
1. PDF 文本层可读时，优先使用文本层。
2. 文本层质量差时，允许进入 OCR / 图像理解补充路径。
3. 失败记录必须可见，不能静默吞掉。
4. 解析失败不应破坏知识库其他对象可用性。

### 5.3 模块 M3：资产对象模型

#### 5.3.1 设计目标
把图片、流程图、截图、扫描页从“附件”提升为“可识别、可命中、可引用、可回溯”的知识对象。

#### 5.3.2 资产定义
资产是文档中的非纯文本知识载体，包括但不限于：
1. 图片；
2. 流程图；
3. 截图；
4. 扫描页；
5. PDF 页面图像区域；
6. 后续扩展的图表、表格截图等视觉对象。

#### 5.3.3 资产必须具备的字段语义
从产品设计角度，资产至少需要表达：
- 资产标识；
- 所属知识库；
- 宿主文档；
- 来源位置；
- 预览能力；
- 可被检索 / 可被引用状态；
- 与证据对象的关联关系。

#### 5.3.4 资产与宿主文档的关系
1. 资产可来源于宿主文档，但不应被宿主文档完全吞没。
2. 在浏览上，资产可以作为文档详情的一部分出现；
3. 在检索上，资产应允许被独立命中；
4. 在回答上，资产应允许被直接引用；
5. 在追溯上，资产必须能回到宿主文档和具体位置。

#### 5.3.5 P0 设计底线
P0 不要求把所有视觉理解做到极致，但至少要满足：
1. 资产对象可被识别并展示；
2. 资产可以成为证据来源之一；
3. 资产不是仅在附件列表里被动挂着；
4. 至少支持“被独立命中或被直接引用”的产品定义闭环。

### 5.4 模块 M4：单知识库检索与问答

#### 5.4.1 设计目标
先在明确知识边界内证明问答闭环成立，而不是急于做跨库大杂烩检索。

#### 5.4.2 功能定义
问答模块负责：
1. 接收用户问题；
2. 明确当前问题绑定的知识库范围；
3. 执行检索；
4. 生成回答；
5. 绑定证据与来源；
6. 返回可展开的预览。

#### 5.4.3 P0 范围约束
1. P0 默认只做单知识库范围问答。
2. 单知识库必须在界面或会话上下文中显式可见。
3. 如果用户未明确范围，应优先引导选择知识库，而不是隐式跨库搜索。
4. 跨知识库检索、比较、综合总结属于 P1。

#### 5.4.4 回答结果结构
从产品输出角度，一次回答至少应由以下部分构成：
- 结论；
- 证据列表；
- 来源标识；
- 可预览入口；
- 当前知识范围说明。

### 5.5 模块 M5：证据与预览系统

#### 5.5.1 设计目标
让“回答可信”成为产品级默认体验，而不是附加功能。

#### 5.5.2 功能定义
证据模块负责：
1. 把检索命中的片段、页码、资产、定位信息组织成证据对象；
2. 把证据挂到回答结果上；
3. 支持用户查看原文、原页、原图或宿主位置；
4. 支持区分“文本证据”和“资产证据”。

#### 5.5.3 证据对象设计要求
证据对象至少需要表达：
- 证据类型；
- 来源知识库；
- 来源文档 / 资产；
- 定位方式；
- 与回答的关联关系；
- 可预览状态。

#### 5.5.4 体验要求
1. 用户应一眼知道回答“凭什么这么说”。
2. 用户能从回答快速跳到证据。
3. 用户能区分不同证据来自文本还是资产。
4. 证据展示不能打断主回答阅读，但必须足够可见。

### 5.6 模块 M6：范围控制契约

#### 5.6.1 设计目标
在尚未物理隔离前，先建立一个清晰、可审计、默认拒绝的范围控制契约，为未来 Agent 接入与接口开放打基础。

#### 5.6.2 契约对象
范围控制至少涉及三个对象：
1. **请求主体**：用户会话、外部 Agent、插件、自动化脚本等；
2. **被请求范围**：一个或多个知识库；
3. **执行结果**：允许、拒绝、降级处理或返回范围不满足提示。

#### 5.6.3 契约规则
1. 默认拒绝：未显式授权的知识库不得被访问。
2. 显式绑定：每个接入主体都要有可访问知识库清单。
3. 显式声明：每次请求都应包含目标范围，或由系统补全并让用户可感知。
4. 结果可追溯：系统应能看出这次回答是在什么范围下生成的。
5. 失败可见：范围不合法时，应返回清晰拒绝，而不是静默放宽。

#### 5.6.4 P0 阶段的风险接受条件
这是本 FRD 的关键判断：

**P0 阶段允许先建立基于逻辑过滤的范围控制契约，但只在以下前提下可接受：**
1. 产品主场景仍是本地单机、单用户主导使用；
2. P0 不把系统包装成“已具备强安全隔离的外部知识服务”；
3. P0 的外部接入只做“契约预留 / 受控接入设计”，不默认开放为任意第三方 Agent 的广泛调用面；
4. 范围控制必须采用“显式授权 + 默认拒绝 + 请求侧声明 + 结果侧回显”的组合，而不是只依赖隐式过滤；
5. FRD 需要把“当前风险仍存在”写明，不能用文档语言掩盖。

#### 5.6.5 P1 / P2 演进方向
1. **P1**：增强接入主体管理、审计记录、失败反馈和更完整的开放面控制。
2. **P2**：引入物理隔离 / 独立命名空间，把范围控制从“契约 + 逻辑过滤”升级为“契约 + 更强隔离”。

### 5.7 模块 M7：外部接入与授权模型

#### 5.7.1 设计目标
为未来外部 Agent / 插件 / 自动化流程接入知识平台提供稳定边界，但不强行把当前自研框架推翻重来。

#### 5.7.2 接入主体模型
外部接入主体（Integration Principal）是：
- 一个外部 Agent；
- 一个本地插件；
- 一个自动化脚本；
- 一个受控集成流程。

它不是企业账号系统里的“用户”，而是一个被授予范围的系统主体。

#### 5.7.3 授权模型
每个接入主体至少需要配置：
1. 可访问知识库范围；
2. 可用操作类型，如检索、问答、只读引用等；
3. 是否允许资产级证据返回；
4. 是否需要用户确认或更高风险审批。

#### 5.7.4 开放方式设计
FRD 默认采用双层开放思路：
1. **内层**：继续兼容现有自研 Agent runtime / tool registry / approval 机制；
2. **外层**：为 MCP / 标准接口包装预留稳定对象与范围控制层。

#### 5.7.5 P0 与 P1 边界
1. P0：完成对象模型、范围控制契约和受控接入设计。
2. P1：再推进更实用化的外部 Agent 接入体验。
3. P2：再推进标准化协议层与更强隔离能力。

### 5.8 模块 M8：遗留前端迁移策略

#### 5.8.1 设计目标
解决“Electron 主线”和“Streamlit 遗留 Demo”并存导致的产品叙事摇摆。

#### 5.8.2 设计结论
1. Electron + FastAPI + React 为主线产品壳。
2. Streamlit 视为遗留兼容 / 参考资产。
3. FRD 不要求立即删除 Streamlit，但必须从产品叙事上降级。
4. 新能力设计默认只面向主线信息架构。

#### 5.8.3 迁移原则
1. 新对象模型以主线界面承接；
2. 遗留 Demo 若继续保留，只做兼容展示或内部参考；
3. 不允许未来关键能力只在遗留 Demo 中出现而不进入主线；
4. 最终退场方案留到后续实施阶段决定。

## 6. 核心对象设计

### 6.1 知识库对象
知识库对象应承载：
- 身份；
- 描述；
- 统计；
- 范围；
- 接入策略；
- 生命周期状态。

### 6.2 文档对象
文档对象应承载：
- 来源文件；
- 所属知识库；
- 类型；
- 解析状态；
- 定位能力；
- 与资产的关系。

### 6.3 资产对象
资产对象应承载：
- 资产身份；
- 所属知识库；
- 宿主文档；
- 可预览能力；
- 可检索能力；
- 可引用能力；
- 来源位置。

### 6.4 会话对象
会话对象应承载：
- 提问；
- 范围；
- 回答；
- 证据；
- 时间线；
- 操作记录。

### 6.5 证据对象
证据对象应承载：
- 来源类型；
- 来源对象；
- 定位信息；
- 与回答关系；
- 预览能力。

### 6.6 Integration Principal 对象
Integration Principal 对象应承载：
- 主体身份；
- 范围绑定；
- 可用动作；
- 风险等级；
- 审批要求；
- 审计信息。

## 7. 关键交互流程

### 7.1 知识沉淀流程
创建知识库 → 选择知识库 → 导入文档 → 解析与资产发现 → 查看对象状态 → 完成索引。

### 7.2 单库问答流程
选择知识库 → 输入问题 → 执行检索 → 生成回答 → 展示证据 → 预览原文 / 原图。

### 7.3 受控接入流程
创建 Integration Principal → 绑定允许访问的知识库 → 指定可用动作 → 发起受控请求 → 返回带范围标识和证据的结果。

### 7.4 范围不合法流程
发起请求 → 检测范围未授权 / 不明确 → 拒绝执行或要求重选范围 → 返回清晰提示。

## 8. 信息架构与页面设计映射

### 8.1 页面级映射
建议主线页面映射如下：
1. 知识库列表页：承接 M1。
2. 知识库详情页：承接 M1 + M2 + M3 + M4 + M5。
3. 文档页签：承接导入与解析状态。
4. 资产页签：承接独立资产浏览与引用入口。
5. 问答页签：承接单库问答与证据展示。
6. 设置 / 接入页签：承接范围控制与外部接入配置。

### 8.2 页面行为约束
1. 问答页必须始终可见当前知识范围。
2. 资产页不能只是附件列表。
3. 接入页必须围绕“范围绑定”设计，而不是围绕“万能访问”设计。
4. 遗留 Streamlit 不纳入新主导航设计。

## 10. 关键设计决策

### 10.1 决策一：FRD 不再把“知识库是一等对象”写成文档口号
上一轮 PRD 里仍有一条偏“文档写法要求”的表达。到 FRD 阶段，应统一改成真实功能约束：
- 任何核心对象都必须可归属到知识库；
- 任何核心问答都必须可回显知识范围；
- 任何外部接入都必须以知识库作为授权最小单元。

### 10.2 决策二：P0 阶段允许“契约先行，隔离后补强”
这是一个有前提的设计结论，而不是安全乐观主义：
1. P0 可以先设计并落地范围控制契约；
2. 但 P0 不应把这种能力包装成高安全隔离外部服务；
3. 真正更强的安全边界要在 P2 通过物理隔离 / 独立命名空间增强；
4. 因此 FRD 必须始终把“当前风险存在”作为显式说明，而非备注。

### 10.3 决策三：外部开放采用“双层演进”而不是“直接替换”
1. 内层兼容现有自研 Agent runtime；
2. 外层预留标准化包装；
3. 对外契约优先稳定对象和范围，不急于先定协议之争。

### 10.4 决策四：遗留前端先降级叙事，再决定退场路径
1. 先统一主线；
2. 再谈迁移实施；
3. 避免在功能设计阶段同时维护两套平权产品叙事。

## 11. P0 阶段验收判断建议
P0 阶段功能设计完成后，后续实施与验收至少应围绕以下判断：
1. 用户是否能清晰感知知识库边界。
2. 文档与资产是否都进入统一对象模型。
3. 单知识库问答是否形成证据化闭环。
4. 资产是否能独立命中或被直接引用。
5. 范围控制是否做到默认拒绝、显式绑定、结果回显。
6. 产品文档是否没有把“逻辑隔离”误写成“物理隔离”。

## 12. 当前未决但需在后续文档继续跟进的问题
1. 范围控制契约在 API / UI / Agent tool 层分别如何表达。
2. 资产对象首阶段的最小字段集合与展示密度。
3. 单库问答和未来跨库问答的交互差异。
4. 证据对象在文本与图像之间是否需要统一评分 / 排序口径。
5. 遗留 Streamlit 的实际下线时点。
