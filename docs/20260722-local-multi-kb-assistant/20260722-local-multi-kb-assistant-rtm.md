# 本地多知识库知识助手平台需求追踪矩阵（RTM）

## 1. 文档信息
- 文档版本：v0.1
- 文档状态：基于 PRD v0.4 / FRD v0.1 的首版矩阵
- 创建日期：2026-07-22
- 对应 PRD：`docs/20260722-local-multi-kb-assistant/20260722-local-multi-kb-assistant-prd.md`
- 对应 FRD：`docs/20260722-local-multi-kb-assistant/20260722-local-multi-kb-assistant-frd.md`
- 对应目录：`docs/20260722-local-multi-kb-assistant/`
- 当前阶段：Stage 1 / 需求追踪，不展开实施计划与测试执行

## 2. 文档目的
RTM 用于把本需求从“产品目标”追踪到“功能设计”和“后续验证重点”，避免后续阶段出现：
1. PRD 说得清楚，但 FRD 落不下来；
2. FRD 设计了模块，但后续实施不知道先做什么；
3. 风险被写在文档里，却没有被绑定到后续验证项；
4. P0 / P1 / P2 的边界在后续阶段再次膨胀或被弱化。

## 3. 追踪原则
1. 每条 FR / ER / NFR 都要能映射到一个或多个 FRD 模块。
2. 每条需求都要明确所属阶段：P0 / P1 / P2。
3. 涉及“共享单索引 + `kb_id` 过滤”的需求，必须显式挂出风险与限制。
4. RTM 当前只定义“后续验证重点”，不写具体测试命令与实施步骤。
5. 若后续实现与本矩阵不一致，优先回查 PRD / FRD，再决定是改设计还是改范围。

## 4. 功能需求追踪矩阵（FR）

| 需求 ID | PRD 需求摘要 | 所属阶段 | 对应 FRD 模块 | 核心对象 | 当前关键风险 / 约束 | 后续验证重点 |
|---|---|---|---|---|---|---|
| FR-01 | 知识库管理 | P0 | M1 知识库边界模型 | Knowledge Base | 不能把知识库退化成隐藏过滤参数 | 用户能创建、选择、识别当前知识库；问答结果能回显知识范围 |
| FR-02 | 文档导入与解析 | P0 | M2 文档导入与解析模型 | Document | 解析失败、状态不可见会破坏知识沉淀体验 | Markdown / PDF 导入状态清晰；失败原因可见；来源可追溯 |
| FR-03 | 多模态资产建模 | P0 | M3 资产对象模型 | Asset | 资产容易再次退化为附件模式 | 资产可独立展示、独立命中或被回答直接引用，并可回溯宿主文档 |
| FR-04 | 检索与问答 | P0（单库）/ P1（跨库） | M4 单知识库检索与问答 | Session / Evidence | P0 若隐式跨库，会冲掉边界设计 | P0 仅单库问答；回答前后范围可见；结果与证据绑定 |
| FR-05 | 证据与预览 | P0 | M5 证据与预览系统 | Evidence | 回答若无证据，将回退成黑盒聊天体验 | 回答包含来源、片段 / 页码 / 资产定位、预览入口 |
| FR-06 | 二级组织能力 | P1 | M1 扩展位 | Knowledge Base / Document | 若过早做深，会冲掉“知识库为第一边界” | 二级组织能力只作为扩展位，不破坏知识库边界 |
| FR-07 | Agent 接入能力 | P1（实用化）/ P0（契约预留） | M6 范围控制契约 + M7 外部接入与授权模型 | Integration Principal | 目录级物理隔离若被包装成完整多租户安全服务，仍会产生权限误判 | 默认拒绝、显式绑定、请求侧声明、结果侧回显、拒绝未授权范围 |

## 5. 扩展性需求追踪矩阵（ER）

| 需求 ID | PRD 需求摘要 | 所属阶段 | 对应 FRD 模块 | 当前关键风险 / 约束 | 后续验证重点 |
|---|---|---|---|---|---|
| ER-01 | 数据源扩展能力 | P1 | M2 / 对象层 | 新数据源不应破坏既有对象模型 | 新来源接入后仍归属于知识库、文档、资产体系 |
| ER-02 | 解析器扩展能力 | P1 | M2 / M3 | 扩展解析器时容易把失败路径做成黑盒 | 解析器可扩展，失败回退与状态可见 |
| ER-03 | 检索链路扩展能力 | P1 | M4 / M5 | 引入更多检索方式后不能丢掉范围与证据 | 无论检索策略如何变化，都要保留范围绑定与证据输出 |
| ER-04 | 存储边界扩展能力 | P2（目录级隔离已提前完成） | M1 / M6 / M7 | 历史共享索引数据需要重建；目录隔离不等价于完整权限体系 | 持续验证独立持久化、跨库不可见、迁移说明和纵深范围控制 |
| ER-05 | 接口开放扩展能力 | P1 / P2 | M6 / M7 | 若直接用新协议替代现有框架，容易造成迁移割裂 | 自研 runtime 与 MCP / 标准包装可共存，范围控制层稳定 |
| ER-06 | 版本演进与迁移能力 | P2 | M8 / 对象层 | 迁移过程若破坏已有知识对象，将导致历史失效 | 对象模型升级后，旧知识库 / 文档 / 资产仍可迁移使用 |

## 6. 非功能需求追踪矩阵（NFR）

| 需求 ID | PRD 需求摘要 | 所属阶段 | 对应 FRD 模块 | 当前关键风险 / 约束 | 后续验证重点 |
|---|---|---|---|---|---|
| NFR-01 | 可理解性 | P0 | M1 / M4 / M5 | 如果用户看不懂当前范围与来源，边界设计会失效 | 用户能理解当前知识库、当前回答范围、当前证据来源 |
| NFR-02 | 可维护性 | P0 | M1-M8 全部 | 模块边界不清会让后续功能继续耦合 | 对象层、处理层、体验层、开放层分层清晰 |
| NFR-03 | 可扩展性 | P0-P2 | M1-M8 全部 | 新格式 / 新接口加入时可能破坏对象层 | 新能力优先挂接既有对象模型，不重定义核心对象 |
| NFR-04 | 本地可用性 | P0 | M2 / M4 / M5 | 若关键链路依赖外部服务，将偏离产品定位 | 本地环境可完成核心导入、问答、证据预览闭环 |
| NFR-05 | 可观察性 | P0 | M2 / M5 / M6 | 导入、检索、授权过程若不可见，无法定位问题 | 解析状态、范围判断、证据来源、拒绝原因可见 |
| NFR-06 | 安全边界 | P0-P2 | M6 / M7 / ER-04 | 当前逻辑过滤不是强隔离；过滤失效即越权访问风险 | P0 不夸大安全性；P1/P2 按计划补强范围控制与隔离边界 |

## 7. 阶段范围追踪矩阵（P0 / P1 / P2）

### 7.1 P0：验证知识底座是否成立
| P0 项 | 对应需求 | 对应 FRD 模块 | 当前设计结论 |
|---|---|---|---|
| 知识库对象成立 | FR-01 | M1 | 知识库是产品对象、问答范围对象、授权最小单元 |
| 本地导入与解析 | FR-02 | M2 | 首批覆盖 Markdown / PDF，并保留来源与状态 |
| 资产对象建模 | FR-03 | M3 | 资产不是附件，必须能独立展示 / 引用 |
| 单库问答 | FR-04 | M4 | P0 只做单知识库问答，避免边界模糊 |
| 证据与预览 | FR-05 | M5 | 证据化输出是默认体验，不是可选装饰 |
| 范围控制契约 | FR-07（契约预留）/ NFR-06 | M6 / M7 | P0 允许契约先行，但不包装成高强度安全隔离服务 |

### 7.2 P1：增强能力
| P1 项 | 对应需求 | 对应 FRD 模块 | 当前设计结论 |
|---|---|---|---|
| 跨库检索 / 比较 | FR-04 | M4 | 在单库闭环稳定后再做跨库能力 |
| 二级组织能力 | FR-06 | M1 扩展位 | 可做文件夹 / 标签 / 专题，但不能破坏知识库边界 |
| 外部接入实用化 | FR-07 / ER-05 | M6 / M7 | 在范围控制契约稳定后再扩大开放面 |
| 更多数据源 / 解析器 / 检索方式 | ER-01 / ER-02 / ER-03 | M2 / M3 / M4 | 增强处理能力，但不推翻对象模型 |

### 7.3 P2：平台化能力
| P2 项 | 对应需求 | 对应 FRD 模块 | 当前设计结论 |
|---|---|---|---|
| 物理隔离 / 独立命名空间 | ER-04 / NFR-06 | M1 / M6 / M7 | 这是安全边界增强，不是可有可无的优化项 |
| 标准化开放接口层 | ER-05 | M7 | 在内层兼容现有框架基础上逐步外包标准协议 |
| 迁移与生态能力 | ER-06 | M8 / 对象层 | 版本演进不能让已有知识资产失效 |

## 8. 风险追踪矩阵

| 风险 ID | 风险描述 | 关联需求 | 关联 FRD 模块 | 当前阶段判断 | 后续必须验证的点 |
|---|---|---|---|---|---|
| RK-01 | 历史共享索引中的非 default 数据不会自动拆分迁移 | FR-07 / ER-04 / NFR-06 | M1 / M6 / M7 | 当前已完成新索引物理隔离，但旧数据需要重建 | 文档明确迁移边界；独立目录持久化和跨库不可见测试必须通过；范围未授权仍拒绝 |
| RK-02 | 资产再次退化为附件，导致“多模态一等对象”失真 | FR-03 / FR-05 | M3 / M5 | 高风险产品退化点 | 资产是否可独立命中、直接引用、预览和回溯 |
| RK-03 | 主线产品与遗留 Streamlit 并存，导致叙事摇摆 | PRD 3.1 / ER-06 | M8 | 已在文档上降级遗留地位，但代码现实仍共存 | 新能力是否只面向主线信息架构；遗留入口是否不再承接新主能力 |
| RK-04 | P0 范围膨胀，提前做跨库、复杂 Agent、平台化开放 | FR-04 / FR-07 / ER-05 | M4 / M6 / M7 | 需严格控范围 | 单库优先、契约预留优先、平台化能力不前置 |
| RK-05 | 自研 runtime 与 MCP 方向被误写成替换关系 | ER-05 | M7 | 已在 PRD / FRD 中纠正为共存设计 | 后续接口设计是否保持对象层和范围控制层稳定，不出现协议先行绑架 |

## 9. 关键追踪结论
1. 当前最需要被持续追踪的不是“功能够不够多”，而是“边界说法是否诚实”。
2. 截至 2026-08-17，P0/P2 之间原定的物理索引边界已经提前落地；当前验收必须同时确认：
   - 知识库对象和资产对象是否成立；
   - 单库问答是否证据化；
   - 范围控制契约是否清晰；
   - 非 default KB 是否使用独立文件集并在重载后保持跨库不可见；
   - 文档是否明确历史数据重建和正式发布边界。
3. 后续 P1 / P2 重点转向迁移工具、权限模型和标准化开放层，而不是重复实现已完成的目录级物理隔离。

当前仓库里除本轮正式文档外，仍保留一批更早期的产品 / 方案类文档，但已不再继续停留在 `docs/` 根目录主入口位置，而是分层处理为：
- `docs/archive/root-legacy-20260724/`：从 `docs/` 根目录迁出的历史原件快照（如 `agent_v1_prd.md`、`agent_v1_frd.md`、`agent_v1_rtm.md`、`agent_v1_execution_plan.md`、`agent_v1_dev_readiness_checklist.md`、`knowledge_agent_product_plan.md`）；
- `docs/archive/superseded-20260722-local-multi-kb-assistant/`：补充了“已被替代 / 已归档”语义说明的整理归档版本；
- `docs/archive/agent_kb_design.md`：更早期的设计材料；
- 以及若干仍待后续治理的偏桌面壳 / 旧叙事设计文档。

建议按以下原则处理，而不是立即直接删除：

### 10.1 什么可以直接覆盖
1. **同一需求目录下的同名文档**可以直接覆盖，例如当前目录下的 PRD / FRD / RTM。
2. 不建议为同一需求再额外新建 `-v2`、`-final`、`-new` 等并行文件名，避免形成多套基线。

### 10.2 什么不建议现在直接删除
1. 已迁入 `docs/archive/` 的历史产品文档、旧 PRD / FRD / RTM，不建议在当前轮继续物理删除。
2. 原因不是它们还正确，而是：
   - 可能仍被历史讨论或 README 引用；
   - 可能还保留上下文价值；
   - 我们需要保留“正式基线 / 历史原件 / 整理归档版”之间的追溯关系。

### 10.3 推荐的处理顺序
推荐顺序是：
1. **当前需求目录内的 PRD / FRD / RTM 成为唯一正式基线**；
2. 对旧文档先做“已被替代 / 历史归档”标记或移入 `docs/archive/`；
3. 等后续确认没有引用依赖后，再决定是否进一步精简 archive 内的重复版本。

### 10.4 当前结论
**现在适合“覆盖当前这套正式文档”，也适合“把根目录旧方案迁出到 archive”，但不适合“彻底删除所有历史方案文档”。**

更准确地说：
- 新基线：应覆盖并收敛到 `docs/20260722-local-multi-kb-assistant/`；
- 历史原件：应迁入 `docs/archive/root-legacy-20260724/` 保留追溯；
- 整理归档版：应保留在 `docs/archive/superseded-20260722-local-multi-kb-assistant/` 作为 superseded 说明层。
