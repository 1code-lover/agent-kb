# 20260825 P0/P2 Status Closure Interview Pack

## 1. 目标

这份 `interview-pack` 的目标是把 **1~30 轮问题**压缩成一个更适合面试、汇报和复盘的结构，不再按轮次流水账讲，而是统一收口成：

- 6 个主题；
- 1 条总判断；
- 1 套推荐话术；
- 1 份“不要怎么讲”的边界提醒。

配套阅读顺序建议：

1. `20260825-p0-p2-status-closure-interview-complete-guide.md`
2. `20260825-p0-p2-status-closure-interview-script.md`
3. `20260825-p0-p2-status-closure-status-report.md`
4. `20260825-p0-p2-status-closure-evidence-cheat-sheet.md`
5. `docs/interview/ThinkRAG_面试问答.md`

---

## 2. 一条总判断

如果一定要把 1~30 轮问题压成一句话，我建议统一这样讲：

> 这 30 轮的核心不是把一个 demo 从 0 做到 1，而是把一个“已经有能力雏形的本地知识库系统”逐步收口成：**主能力闭环更完整、系统契约更一致、验证证据更扎实，但工程完成度仍在继续追赶能力完成度**。

这句话的好处是：

- 不会把项目讲得过小，只像一个课程作业；
- 也不会把项目讲得过满，好像所有问题都已经清零。

## 3. 把 1~30 轮问题压成 6 个主题

### 主题 A：把“能回答”升级成“受控边界内能回答”

这一类问题的核心不是模型效果，而是**问答范围是否受控**。

可以归到这个主题里的问题包括：

- `basic` 模式和 `single_kb` 约束冲突；
- 项目主入口与产品口径不一致；
- 前端把某些模式讲成“全局检索”，但后端并不允许。

推荐讲法：

> 我不是只追求能答，而是先把“答的边界”做对。现在 `basic` / `knowledge` 都显式绑定 active KB，后端也按 `single_kb` 执行，这样产品语义和系统约束是一致的。

### 主题 B：把“参数存在”升级成“参数真的生效”

这一类问题的重点是：很多系统表面上有配置项，但它未必真的打进主链路。

可以归到这个主题里的问题包括：

- QueryRequest 请求级参数疑似没有完整打进 chat 主链路；
- Prompt 契约和后处理边界不清；
- 一些 request-level 选项只停留在前端透传。

推荐讲法：

> 我做的一件很实际的事，是把请求级参数从“前端表单字段”变成真正影响 runtime query engine 的输入，这样优化和调参才不是假动作。

### 主题 C：把“接口返回成功”升级成“用户体验一致”

这一类问题看上去不像算法问题，但直接决定用户会不会信系统。

可以归到这个主题里的问题包括：

- 前端把 query 成功和 history 成功绑死；
- query 已经成功，但 history 慢一拍导致 UI 表现失败；
- 局部成功和全局失败状态混在一起。

推荐讲法：

> 我补的不是表面提示语，而是状态一致性：query 成功优先，history 只负责后续同步，不再让慢一拍的回写把刚返回的答案覆盖掉。

### 主题 D：把“功能堆出来”升级成“能被验证”

这一类问题的核心是：有没有成体系的验证，而不只是零散测试。

可以归到这个主题里的问题包括：

- refusal / negative contract 覆盖不足；
- 缺少对 scope / evidence / preview 的系统证明；
- 很多结论只能靠口头说，不能靠测试和评测坐实。

推荐讲法：

> 我比较强调 layered eval、contract test 和主链路回归，是因为我不想把系统稳定性建立在“感觉最近还行”上，而是建立在可复跑、可复核的证据上。

### 主题 E：把“能开发”升级成“能长期维护”

这一类问题的重点是工程治理，而不是单条功能。

可以归到这个主题里的问题包括：

- 启动链路 / 桌面链路硬编码；
- Docker / requirements / 启动脚本配置漂移；
- 仓库根目录临时文件、日志、调试脚本过多；
- 日志与临时产物治理不规范。

推荐讲法：

> 我不是只补功能，也在持续做工程收口，包括 startup contract、requirements profile、docker smoke、cleanup 和 repo hygiene。这些工作短期不一定最显眼，但决定系统能不能被后续稳定维护。

### 主题 F：把“做完一堆事”升级成“会讲清楚自己做了什么”

这一类问题的重点是表达，而不是实现。

可以归到这个主题里的问题包括：

- 文档闭环不够满；
- 面试表述混淆能力完成度和工程完成度；
- 1~30 轮问题如果按时间线讲，会非常散。

推荐讲法：

> 我现在会主动把项目讲成两层：第一层是主能力闭环已经完成到哪里，第二层是工程完成度还差在哪里。这样既不会过度包装，也不会把真实价值讲小。

## 4. 当前最适合记住的“4 句话骨架”

以后如果只能记很少的话，我建议只记下面 4 句：

1. **这不是简单接模型的 demo，而是本地优先知识库助手的闭环系统。**
2. **我做的重点是把 scope、evidence/preview、请求级参数和前端状态一致性做成可验证的主链路。**
3. **现在主能力闭环已经比较完整，但工程治理还在继续追赶。**
4. **所以我会主动区分能力完成度和工程完成度，而不是把它包装成“已经完全 finished”。**

---

## 5. 当前最适合讲的“3 个亮点 + 3 个边界”

### 5.1 三个亮点

#### 亮点 1：边界做对了
- `basic` / `knowledge` 不再伪装成“全局检索”；
- single-kb scope 成为真正的主路径约束；
- product semantics 与 backend contract 一致。

#### 亮点 2：主链路做实了
- QueryRequest 请求级参数真正进入 runtime；
- query 成功与 history 回写解耦；
- evidence / preview 返回不只是展示字段，而是可核对能力的一部分。

#### 亮点 3：验证做成体系了
- chat 主链路、open api、scope 契约、eval contract、startup / docker / cleanup 都有实际回归；
- 现在不是只有一组漂亮分数，而是多层证据一起支撑项目状态。

### 5.2 三个边界

#### 边界 1：legacy 兼容层还没完全退场
- compatibility wrapper 还存在；
- Streamlit 已经不是主入口，但还保留 opt-in 兼容路径。

#### 边界 2：负向评测还可以继续做深
- refusal / negative contract 已经进入正式套件，而且 hard 集 refusal follow-up 与 main 集 answerable follow-up 都有正式 gate；
- 但 semireal hard negatives 和真实追问型失败场景还值得继续补。

#### 边界 3：heuristic 复杂度还没有被完全消灭
- 已经做了模块化拆分；
- 但不能把当前状态讲成“已经完全由干净契约驱动”。

## 6. 面试时尽量不要这样讲

### 6.1 不要说

- “现在所有问题都解决了。”
- “现在指标都是 1.0，所以系统已经很完美。”
- “工程化问题不重要，核心是答题效果。”
- “OCR 不重要，没人关心。”

### 6.2 建议改成

- “主能力闭环已经完成，但工程收口仍在继续。”
- “当前 pass rate 证明的是定义好的能力闭环被打通，不代表所有真实场景都没有问题。”
- “工程治理不是附属品，它决定系统能不能长期稳定演进。”
- “OCR 不是唯一核心指标，但属于知识接入质量的一部分，不能完全忽略。”

---

## 7. 如果被要求按时间线讲，该怎么收口

如果面试官坚持问“那你 1~30 轮到底怎么推进的”，建议不要逐轮背流水账，而是这样收：

1. **前几轮**：先把主能力能不能成立的问题收住；
2. **中间几轮**：把 scope、preview、evidence、QueryRequest、前端状态这些核心契约做对；
3. **后几轮**：开始把 startup、docker、requirements、cleanup、文档和 interview 材料这些工程治理收口；
4. **当前阶段**：主能力闭环已经形成，重点转向工程完成度继续追赶。

这样既保留了“持续演进”的感觉，又不会显得自己只是在堆小修小补。

---

## 8. 最后的一句话收口

> 如果把 1~30 轮问题压成一句最准确的话，那就是：我已经把这个项目从“能力雏形”推进到了“能力闭环 + 契约闭环 + 证据闭环”，接下来继续补的是工程完成度，而不是重新证明这个系统能不能做出来。

## 10. 被点问单条问题时的回答模板

### 10.1 已收口类问题怎么答

推荐结构：

1. **先说结论**：这条已经收口，当前更多是回归守护项；
2. **再说动作**：我具体改了哪个主链路 / 哪个契约；
3. **最后说边界**：后续主要是防止回归，而不是重新定义架构。

示例句式：

> 这条现在我会定义为“已收口”。因为我已经把产品语义和系统约束对齐了，并且补了自动化回归。后续重点不是再推翻重做，而是防止新入口或新改动绕过已有约束。

### 10.2 大体收口 / 部分完成类问题怎么答

推荐结构：

1. **先说已经做了什么**：自动化 gate、兼容层退场、文档统一、模块化拆分等；
2. **再说为什么不能报完成**：历史兼容层仍在、hard negative 还不够、heuristic 仍偏重、hygiene 还没彻底简化；
3. **最后说下一步**：给出 1 个最具体的后续动作，不要泛泛说“继续优化”。

示例句式：

> 这条我不会讲成“完成”，而会讲成“大体收口”或“部分完成”。因为最大风险已经被自动化约束住了，但历史包袱还没彻底清零。下一步我会继续做更具体的一项，比如补 hard negative、减少 compatibility wrapper，或者继续压缩 heuristic 隐式复杂度。

### 10.3 面试时最稳的总收口句

> 我不会把 12 个问题讲成“全部清零”，而会讲成：核心能力闭环已经完成，最大的工程风险已经被收口成可测试、可回归、可解释的边界；剩余工作主要是继续减少兼容层、增强负向评测和推进治理规范化。
